# Plan 30-03: Ship The Cross-Platform Media-Player Button

<objective>
Finish the phase with the second real built-in family the user asked for: a media-player button that can show current playback state and control play/pause without widening the runtime contract. This slice is deliberately separate from system-status because media control has different platform risk, different truthful-degradation rules, and a locked interaction model that deserves its own end-to-end proof, while still reusing the new shared helper surface for the progress treatment Phase 30 introduced.
</objective>

## Tasks

<task id="30-03-01">
<title>Create the shared media-controller seam with honest per-OS adapters</title>
<files>
- packages/cli/src/system/media-controller.ts
- packages/cli/src/system/linux-media-controller.ts
- packages/cli/src/system/macos-media-controller.ts
- packages/cli/src/system/windows-media-controller.ts
</files>
<action>
Create a shared media-controller contract that exposes truthful playback status (`play`, `pause`, `stop`), best-effort metadata fields, progress information, and a play/pause toggle command. Keep OS selection outside the button renderer by branching through normalized host context in the controller layer. For Linux, implement the first adapter on a documented MPRIS path using either `playerctl` subprocess integration or the already-present `dbus-next` dependency, and make the code/comments explicit about progress limits because MPRIS `Position` is not a continuously pushed property. For macOS and Windows, add adapter entry points that can return unsupported or partial data honestly until their deeper implementations are verified; do not fabricate parity.
</action>
<verify>
Run `grep -n "play\|pause\|stop\|unsupported\|playerctl\|dbus" packages/cli/src/system/media-controller.ts packages/cli/src/system/linux-media-controller.ts packages/cli/src/system/macos-media-controller.ts packages/cli/src/system/windows-media-controller.ts`.
</verify>
<done>
The repo has one explicit media-controller seam with per-OS adapters and an honest unsupported path, so the button layer no longer needs to know platform-specific media control details.
</done>
</task>

<must_haves>
- Do not make tap configurable; tap must stay fixed to play/pause per the locked Phase 30 decision.
- Do not create a custom marquee or scrolling subsystem for media text; reuse `Text fit="marquee"`.
- Do not promise equal metadata depth on all operating systems when the adapter cannot verify it.
</must_haves>

<task id="30-03-02">
<title>Register the media-player built-in through the real addon/config/runtime path</title>
<files>

<action>
Create a bundled `media-player` addon with a mounted button definition that renders playback status, title/artist, app/source name, and completed percent through the shared helper surface, using `Bars` for the progress treatment and `Text fit="marquee"` for overflowing metadata. Keep `onTap` fixed to play/pause through the media-controller seam and expose only optional hold configuration through schema/config. Register the addon in `packages/cli/src/addon/builtin.ts` and extend config validation in `packages/cli/src/core/schemas.ts` only as far as needed for the new built-in payload. Add focused tests in `packages/cli/src/builtin-addons/media-player/index.test.ts` that prove the built-in registers through the shipped addon path, preserves truthful `play|pause|stop` semantics, uses the shared helper-backed progress rendering, and degrades honestly when metadata or platform support is partial.
</action>
<verify>
Run `pnpm --filter sireno-deck-cli exec vitest run src/builtin-addons/media-player/index.test.ts src/addon/loader.test.ts src/deck/runtime.test.ts`.
</verify>
<done>
Users can configure a real built-in media-player button that loads through the product's normal addon/runtime path, shows truthful playback state plus best-effort metadata, and toggles play/pause on tap without hidden platform magic in the renderer.
</done>
</task>
