# Plan 29-02: Split Date-Time And Normalize It To Day.js

<objective>
Turn the date-time addon into the first full built-in proof of Phase 29: one button definition per file, TSX-first authoring, and an honest `dayjs` formatting contract for the existing digital/locked/analog/calendar surfaces. This slice is the right second step because it exercises both the structural split rule and the formatter normalization the user asked for, while staying within the current addon capability boundary.
</objective>

## Tasks

<task id="29-02-01">

<files>

- packages/cli/src/builtin-addons/date-time/buttons/calendar-sheet.tsx
- packages/cli/src/builtin-addons/date-time/schemas.ts
</files>
<action>
Refactor the built-in date-time addon so `packages/cli/src/builtin-addons/date-time/index.ts` becomes a clean registry file that re-exports four separate button-definition modules: the existing digital date-time button plus new `locked-time-tile`, `analog-clock`, and `calendar-sheet` files under `buttons/`. Move any reused schemas, config defaults, constants, and helper exports into nearby support files such as `schemas.ts` so the split does not duplicate logic or break the current test surface. Keep the existing button ids and addon registration semantics stable so runtime lookups like the locked-time tile fallback path do not need a new capability or registry model.
</action>
<verify>
Run `pnpm --filter sireno-deck-cli exec vitest run src/builtin-addons/date-time/index.test.ts src/deck/runtime.test.ts`.
</verify>
<done>
The date-time addon has explicit per-button ownership without losing the stable registry surface or the runtime-visible built-in button ids the rest of the product depends on.
</done>
</task>

<must_haves>
- Do not broaden the date-time addon into the deferred richer formatting DSL; Phase 29 only normalizes the existing `date_format` / `time_format` contract.
- Keep live visual buttons like analog clock inside the existing render/deck-button seam instead of inventing a broader renderer API.
- Preserve stable file-relative test proof while moving helpers and button modules.
</must_haves>

<files>
- packages/cli/package.json

- packages/cli/src/builtin-addons/date-time/buttons/date-time.tsx

<action>
Add `dayjs` to `packages/cli/package.json`, extract the date/time formatting logic into a dedicated support module such as `packages/cli/src/builtin-addons/date-time/format.ts`, and rewrite the digital date-time formatter so `date_format` and `time_format` use Day.js token syntax as the real shipped contract. Be explicit about token breadth during execution: if the product supports localized or advanced Day.js token families, wire the required plugins in this module and lock them with tests; if not, keep the supported token surface intentionally narrower and make the tests/examples reflect that exact contract. Update the focused date-time tests so the digital label path, locked-time helpers, and any config-facing examples all describe the real Day.js-backed behavior instead of the old token replacement map.
</action>
