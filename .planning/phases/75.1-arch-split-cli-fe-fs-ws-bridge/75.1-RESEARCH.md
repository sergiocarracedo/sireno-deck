# Phase 75.1 Research — Architecture split: CLI / Frontend Server / Frontend + WebSocket bridge

<summary>
The refactor moves runtime rendering from a Node-side `react-reconciler` (`packages/cli/src/render/dom-host/`) to a Vite-served React app rendered in Chromium (headless for real mode, user browser for emulation). The CLI keeps hardware, command execution, and global state; adds two new subsystems — a supervised Vite child process and a `ws.Server`-based WebSocket bridge on localhost. The `BrowserLauncher`/`BrowserLike`/`BrowserPageLike` abstraction stays; the launch target changes from in-process Node to Chromium pointing at Vite. Built-in addons need no code changes (they already export React TSX); they reach the Vite bundle through the existing addon registry.

Tracer-bullet scope: prove the new pipeline end-to-end on one existing deck (one builtin addon) before scaling to overlay decks, navigation history, emulator panels, and the full addon surface.
</summary>

<scope>
## In Scope (this phase)

- New `packages/cli/frontend/` Vite app: router, deck/button components, WS client.
- New `packages/cli/src/render/ws-bridge.ts`: `ws.Server` on `127.0.0.1:WS_PORT`, message router for `deck-config` / `state` / `button-config` (CLI → runner) and `button-action` / `snapshot` / `method-call` (runner → CLI).
- New `packages/cli/src/render/frontend-server.ts`: spawn Vite as a supervised `child_process.spawn` Node process; consume stdout/stderr to pino; restart on crash up to N times.
- New `packages/cli/src/render/browser-runner.ts`: Playwright Chromium wrapper that connects to the Frontend Server URL and bridges its page-level WS client to the CLI's WS bridge.
- Retire `packages/cli/src/render/dom-host/` entirely. Single render path.
- One vertical-slice tracer bullet proves the new pipeline end-to-end on one existing deck + one builtin addon (date-time recommended as the reference surface — already exports React TSX, used everywhere).
- WS message schema documented with a `protocolVersion` field (independent from `SIRENO_ADDON_API_VERSION`; the bridge has its own concerns).

## Out of Scope (deferred)

- Full addon-surface migration (overlay decks, system-status, value-display, etc.) — proves the tracer bullet first, then sweep.
- Router library decision — React Router v7 chosen as default (matches the React 19 + Vite stack).
- Production build path (bundled CLI without Vite dev server).
- Hot-reload of addon manifest changes (new button type registered) — still requires CLI restart.
- Multi-device / multi-bridge coordination.
- Delta snapshot diffing — keep full-snapshot semantics from Phase 35.
</scope>

<external_research>
## Library / API Findings (Context7-verified)

### Vite programmatic API
- Standalone dev server: `createServer({ configFile, root, server: { port, host, strictPort } })` returns a ViteDevServer with `listen()`, `close()`, `printUrls()`, `ws` (the HMR socket), and `transformRequest()` hooks.
- For our case (Vite as a child Node process), the child entry script does: `import { createServer } from 'vite'; const server = await createServer({...}); await server.listen();`. The child prints the bound URL on stdout — the parent parses it for logging. Stdout is line-delimited.
- Vite's HMR socket is on the same HTTP port by default; headless Chromium connecting to Vite picks up HMR automatically. No separate HMR wiring needed.

### WebSocket library
- `ws` is the de-facto Node WS library; `ws.Server({ port, host: '127.0.0.1' })` is the minimal API.
- Client side in the browser: `new WebSocket('ws://127.0.0.1:<port>')` — no extra dependency needed. Ships in every browser and Node 22+.
- Reconnect: `ws` supports built-in `reconnection` on the server (broadcast on reconnect) and the client must handle `onclose` → `setTimeout(() => new WebSocket(...), 1000)`. For the headless browser in real mode, reconnect on Vite restart is critical.

### React Router v7 (chosen for this phase)
- `createBrowserRouter([...routes])` + `<RouterProvider router={router} />`. Works under Vite dev (Vite's HMR doesn't fight the browser history).
- History stack semantics: `navigate(path)` pushes history; `navigate(path, { replace: true })` replaces. Overlay decks call `replace`; regular decks call default `push`.
- `useNavigationType()` returns `PUSH` / `POP` / `REPLACE` — useful for back-button handling on the deck side.

### React 19 + Vite compatibility
- Vite 5+ + React 19 + `@vitejs/plugin-react` 4+ is the current stable combo. `@vitejs/plugin-react` provides Fast Refresh for components.

### Playwright + Vite-served app
- Existing `BrowserLauncher` / `BrowserLike` / `BrowserPageLike` abstraction stays. `BrowserPageLike.goto(url)` already supports external URLs — switch from `file://` (current startup-placeholder path) to `http://127.0.0.1:<vite-port>`.
- Headless flags: reuse the existing `chromium-detect.ts` Playwright Chromium launch defaults.

### Addon frontend surface contract
- Vite supports dynamic `import()` of arbitrary paths at dev-time. Addons can register a `frontend` entry in their manifest; the React app does `import(/* @vite-ignore */ addonManifest.frontend)` at mount time. Vite resolves the path and serves the module.
- For bundled addons: entry is a TS/TSX file under `packages/cli/src/builtin-addons/<name>/frontend.tsx`. For raw-source addons: entry is whatever the manifest declares, Vite serves it from disk.
- Tradeoff vs static registration: dynamic `import()` keeps startup fast and lets addons mount/unmount without restart. Static registration requires the addon list up front (which we already have from CLI-side addon loading).
- **Choice for this phase**: dynamic `import()` from addon manifest `frontend` entry. Matches the diagram's "addon frontend components" pipe.
</external_research>

<existing_patterns>
## Codebase Patterns to Reuse

- **Process supervision** (yargs command structure, `startDaemon` / `stopDaemon`, pino logging) — new Vite child process supervisor follows the same shape: stdout/stderr → pino, `exit` event → restart or fatal.
- **Snapshot pipeline**: `Chromium page → Playwright screenshot → sharp → write cache → device`. Sharp + write cache stays in CLI; only the render source changes (was `renderDomDeck → sharp`, now `Playwright screenshot → sharp`).
- **Config validation** (`packages/cli/src/core/schemas.ts`) — no schema changes needed.
- **Theme / addon asset pipeline** (`addon://` and `theme://` URL rewriting) — reused as-is.
- **Addon registry** (`packages/cli/src/addon/`) — stays in CLI; addon manifests still load via the existing path; only their `render()` method consumers change.
- **Built-in addon surfaces** (TSX in `packages/cli/src/builtin-addons/`) — already React TSX; move from in-process reconciler to Vite-served bundle. No addon code changes.
- **Built-in date-time** is the reference builtin — already exports React TSX, used everywhere, has simple layouts and a polling data path. Best tracer-bullet candidate.
</existing_patterns>

<risks>
## Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Vite child process crash leaves CLI hanging | `exit` event handler with restart-up-to-N (3 attempts), then fatal + clean shutdown of all subsystems |
| Headless Chromium cold-start latency kills Phase 35 performance goal | Per-session lifecycle (one browser, SPA navigates) — cold-start is once per CLI session, not per deck change |
| WS bridge port clashes in dev | Auto-select via port 0 binding, log the chosen port. Frontend Server port also auto-selected. |
| WS client in headless browser doesn't reconnect on Vite restart | Client-side reconnect with 1s backoff; CLI queues outbound `deck-config` until at least one client is connected |
| dom-host retirement breaks tests that import from `packages/cli/src/render/dom-host/` | Inventory call sites first; plan the deletion as its own small commit; add an alias or test fixture in the new frontend so tests that need the surface component still find it |
| Snapshot diffing stays full-snapshot — Phase 35 perf goal unaffected | Confirm: the perf concern was resampling cadence, not payload size. Per-session lifecycle + SPA navigation means the page only rerenders when config changes. |
| Addon manifest `frontend` entry doesn't exist for legacy addons | Phase ships one reference addon (date-time) with `frontend` registered; existing addons without `frontend` get a clear "renderer not registered" error from the loader seam |
| React 19 Fast Refresh conflicts with the addon registry | `@vitejs/plugin-react` 4+ handles Fast Refresh natively; addons are just modules, no special treatment |
</risks>

<plan_structure>
## Plan Structure (vertical slices — tracer bullets)

Four plans, each demoable end-to-end. Sequential (parallelization disabled in config).

### Plan 75.1-01: Foundation — Vite child process + React shell
- Spawn Vite as supervised child Node process from `start.ts`.
- New `packages/cli/frontend/` Vite app with a single React page that renders a hardcoded placeholder deck.
- Playwright Chromium connects to Vite URL; screenshot proves the page is live and rendering.
- No WS bridge yet; the React page is just a static placeholder to prove the plumbing.
- Retire `dom-host/` after the new shell renders successfully on real hardware (one button, one deck, screenshot proves).
- **Demoable**: `pnpm start` boots CLI → spawns Vite → spawns headless Chromium → loads Vite URL → screenshot shows the placeholder deck on hardware.

### Plan 75.1-02: WebSocket bridge + deck-config round-trip
- New `ws.Server` on `localhost:WS_PORT`, CLI side.
- React app opens `WebSocket('ws://127.0.0.1:<port>')` on mount; CLI pushes `deck-config`; React renders the deck.
- CLI replaces the placeholder with a real deck config (one existing builtin — date-time recommended) and verifies the React app renders it via WS.
- Snapshot pipeline stays in CLI: Playwright screenshot → sharp → write cache → device.
- **Demoable**: `pnpm start` boots → Vite → Chromium → WS bridge → React receives real deck-config over WS → renders date-time button → screenshot proves it matches the previous in-process render.

### Plan 75.1-03: Router navigation + history vs overlay
- React Router v7 (`createBrowserRouter` + `RouterProvider`).
- Two real decks from the example config: regular decks push history; overlay decks use `replace`.
- Hardware button press → WS `button-action` → CLI → WS `deck-config` for the next deck → React Router navigates → new deck renders.
- `useNavigationType()` exposed for components that need it (back-button, overlay-dismiss).
- **Demoable**: tap a button → next deck pushes history → press hardware back → returns to previous deck. Overlay summon replaces without history.

### Plan 75.1-04: Emulator mode + complete tracer bullet
- Emulator mode serves the same Vite app; user browser opens `http://127.0.0.1:<vite-port>` directly.
- Frontend Server renders the deck placeholder + emulator control panels (device selector, mouse-emulation code) as siblings of the deck iframe (per diagram).
- Iframe loads the React app; emulated button presses flow through the same WS bridge.
- One end-to-end demo: real mode + emulation mode, both rendering the same addon, both receiving button actions, both writing screenshots correctly.
- **Demoable**: `pnpm start` for real mode; `pnpm emulate` opens user browser with emulator panels; both modes render the same date-time deck.
</plan_structure>

<open_questions>
## Questions Resolved During Research

- **Router library**: React Router v7 chosen (matches React 19 + Vite + Fast Refresh; well-documented `replace` semantics for overlay decks).
- **WS schema versioning**: independent `protocolVersion` field on every message; bumped separately from `SIRENO_ADDON_API_VERSION` because the bridge has addon-system-orthogonal concerns (snapshot transport, hardware action encoding).
- **Addon frontend surface contract**: dynamic `import()` from manifest `frontend` entry; one reference addon (date-time) ships with `frontend` registered.
- **Snapshot diffing**: full snapshot retained (Phase 35 semantics); per-session browser lifecycle keeps cold-start cheap enough.
- **Frontend Server port**: auto-select via port 0; chosen port logged and surfaced via CLI startup logs.
- **Vite child supervision**: 3 restart attempts with linear backoff (1s, 2s, 4s); then fatal + clean shutdown.
- **Emulator mouse handling**: outer user-browser page translates mouse coords over the deck iframe into WS `button-action` messages; iframe itself is a pure canvas. Matches the diagram.

## Questions Deferred to Executor

- Headless Chromium flags beyond the existing `chromium-detect.ts` defaults — executor decides if any new flags are needed for the Vite-served app.
- Exact `protocolVersion` value — executor picks `1` and documents in the message schema file.
</open_questions>
