## Don't Hand-Roll

- Do not invent a second OS-introspection stack for Phase 11. The repo already ships `systeminformation` and uses it in `packages/cli/src/system/live-metrics.ts`; it is a cross-platform backend-side system/OS information library, so the planner should prefer reusing it for OS `type` / `variant` / `version` normalization instead of mixing ad hoc `node:os` calls and shell commands across files. [VERIFIED: packages/cli/package.json, packages/cli/src/system/live-metrics.ts] [CITED: https://systeminformation.io/, https://github.com/sebhildebrandt/systeminformation] [HIGH]
- Do not hand-roll D-Bus framing or shell out to `dbus-send` / `gdbus` as the primary runtime integration path for supported Linux lock detection. `dbus-next` is explicitly positioned as a high-level Node DBus library for Linux desktop/mobile integration and already exposes proxy objects plus signal listeners, which is the right abstraction level for a long-running daemon. [CITED: https://acrisci.github.io/doc/node-dbus-next/] [VERIFIED: DuckDuckGo search result for `dbus-next` npm/docs] [MEDIUM]
- Do not fake universal lock support across every platform or desktop environment. The requirements and context already lock the opposite behavior: ship one honest supported path, expose unsupported capability explicitly, and keep the runtime running normally elsewhere. [VERIFIED: .planning/REQUIREMENTS.md, .planning/phases/11-session-config-contracts/11-CONTEXT.md] [HIGH]
- Do not build lock mode by mutating the only live navigation stack in place. `packages/cli/src/deck/controller.ts` currently owns a single stack array, while the Phase 11 context explicitly requires isolated locked-mode navigation plus full pre-lock restore. Planning should therefore introduce an explicit saved-state seam rather than burying lock behavior inside ad hoc `navigateTo()` calls. [VERIFIED: packages/cli/src/deck/controller.ts, .planning/phases/11-session-config-contracts/11-CONTEXT.md] [HIGH]
- Do not turn Phase 11 into a general-purpose config language. `packages/cli/src/config/loader.ts` currently parses YAML straight into validation with no interpolation step, and the phase context only approves the first minimal host-context templating seam. Keep interpolation narrow and host-context-specific. [VERIFIED: packages/cli/src/config/loader.ts, .planning/phases/11-session-config-contracts/11-CONTEXT.md] [HIGH]

## Common Pitfalls

- The easiest planning failure is horizontal slicing: one plan for host types, one for lock detection, one for tests. That would delay the first demoable lock-aware behavior until the end and violate the tracer-bullet rule. Phase 11 should land at least one end-to-end slice where normalized host context reaches a real runtime surface and one end-to-end slice where lock/unlock switching and restore are actually exercised. [VERIFIED: workflow `plan-phase.md`, .planning/ROADMAP.md] [HIGH]
- Linux session-lock behavior is easy to lie about if the implementation only watches one desktop-specific interface and assumes that means broad support. The sources I could verify show at least two relevant seams: `org.freedesktop.login1` session `Lock` / `Unlock` signals on login1, and GNOME-specific screensaver activation methods on the session bus. Planning should document one supported path and classify the rest as unsupported rather than smearing them together. [CITED: https://dbus.freedesktop.org/doc/dbus-tutorial.html, https://notes.zerodogg.org/GNOME/lock-unlock-cli/] [VERIFIED: DuckDuckGo result snippet for `org.freedesktop.login1` lock/unlock signals] [MEDIUM]
- D-Bus integration can hang or become fragile if the runtime treats signals like one-off commands instead of a long-lived bus connection with event listeners. The D-Bus tutorial describes signals as broadcast events on long-lived bus connections, and `dbus-next` mirrors that model with proxy interfaces that are event emitters. Planning should use a persistent detector owned by startup/runtime lifecycle, not per-check shell commands. [CITED: https://dbus.freedesktop.org/doc/dbus-tutorial.html, https://acrisci.github.io/doc/node-dbus-next/] [MEDIUM]
- Config validation error quality can regress if templating is bolted on after schema validation or line-number mapping. The repo has already learned this the hard way: validation metadata must survive schema, loader, and formatter layers. Phase 11 templating should preserve that discipline instead of creating a pre-parse/post-validate blind spot. [VERIFIED: .planning/STATE.md, packages/cli/src/config/loader.ts, packages/cli/src/core/schemas.ts] [HIGH]
- The implicit locked fallback can drift from the shipped visual system if planning invents a one-off rendering path. The bundled date-time addon already provides digital, analog-clock, and calendar-sheet button variants with core-owned refresh cadence, so the default locked fallback should preferably compose those existing primitives rather than adding a bespoke lock-only renderer. [VERIFIED: builtin-addons/date-time/src/index.ts, .planning/phases/11-session-config-contracts/11-CONTEXT.md] [HIGH]

## Existing Patterns in This Codebase

- Runtime-owned behavior already has one clear home: `packages/cli/src/deck/runtime.ts` owns instance creation, command execution wiring, deck activation, render invalidation, and polling setup. Phase 11 host context and lock-mode orchestration should plug into that seam instead of being scattered through addons. [VERIFIED: packages/cli/src/deck/runtime.ts] [HIGH]
- Addon public contracts are narrow and explicit. `CreateAddonButtonInstanceOptions` currently carries only `button`, `config`, `methods`, and `theme`; adding host context here is the most direct way to satisfy the shared-contract requirement without creating hidden runtime getters. [VERIFIED: packages/cli/src/addon/api.ts, .planning/phases/11-session-config-contracts/11-CONTEXT.md] [HIGH]
- Config loading currently follows a disciplined two-stage flow: parse YAML, bootstrap-validate, load addon registry, then fully validate with line-aware `ConfigValidationError`s. Any host-context interpolation seam has to preserve that loader discipline and error reporting path. [VERIFIED: packages/cli/src/config/loader.ts, packages/cli/src/core/schemas.ts, packages/cli/src/config/loader.test.ts] [HIGH]
- The repo already proves command execution through a single adapter, `packages/cli/src/action/executor.ts`, with tests that assert stdout, stderr, exit codes, and timeouts. If command/status execution is to consume host context consistently, planning should thread the canonical context through this adapter boundary or its immediate caller rather than letting buttons format shell strings ad hoc. [VERIFIED: packages/cli/src/action/executor.ts, packages/cli/src/action/executor.test.ts, packages/cli/src/deck/runtime.ts] [HIGH]
- Navigation state today is intentionally tiny: `packages/cli/src/deck/controller.ts` owns one stack, and runtime tests already exercise deck activation and navigation. Phase 11 can extend this by snapshotting/restoring controller state instead of replacing the navigation model outright. [VERIFIED: packages/cli/src/deck/controller.ts, packages/cli/src/deck/runtime.test.ts] [HIGH]
- The repo has a strong habit of reusing existing built-in addon paths for new surfaces rather than creating side channels. The date-time addon already ships sensible cadences and button variants; the implicit locked fallback should likely be a runtime-composed deck that points at those same built-in definitions. [VERIFIED: builtin-addons/date-time/src/index.ts, .planning/solutions/best-practices/bespoke-live-visuals-can-stay-inside-the-deck-button-variant-seam-2026-05-15.md] [HIGH]

## Recommended Approach

- Split the phase into tracer bullets that each deliver a real behavior. The first slice should introduce the canonical host context end-to-end: normalize OS info through a core-owned provider, add the new public addon input seam, and let one real runtime surface consume that same object in render plus command/status execution plus minimal config templating. [VERIFIED: .planning/ROADMAP.md, .planning/phases/11-session-config-contracts/11-CONTEXT.md] [HIGH]
- Use the existing `systeminformation` dependency for OS normalization, then layer a separate session detector on top for the first supported lock-aware path instead of asking one library to do both jobs. For Linux lock events, the strongest verified direction in this session is a long-lived D-Bus listener around the login/session interfaces, implemented through a Node D-Bus client rather than shelling out repeatedly. [VERIFIED: packages/cli/package.json, packages/cli/src/system/live-metrics.ts] [CITED: https://systeminformation.io/, https://acrisci.github.io/doc/node-dbus-next/, https://dbus.freedesktop.org/doc/dbus-tutorial.html] [MEDIUM]
- Model lock mode as a runtime-owned temporary surface with explicit saved pre-lock navigation state. That lets the runtime swap to a configured locked deck or an implicit built-in date/time fallback while keeping the original navigation stack intact for unlock restoration. [VERIFIED: .planning/phases/11-session-config-contracts/11-CONTEXT.md, packages/cli/src/deck/controller.ts, packages/cli/src/deck/runtime.ts] [HIGH]
- Keep config changes narrow: add one top-level runtime/session config entry for an optional locked deck reference, validate it in the existing schema path, and add just enough templating to inject host context without undermining current line-aware error reporting. [VERIFIED: .planning/phases/11-session-config-contracts/11-CONTEXT.md, packages/cli/src/core/schemas.ts, packages/cli/src/config/loader.ts] [HIGH]
- Verification should prove both behavior slices, not just unit seams: loader/schema coverage for the new runtime/session config and templating behavior, addon/runtime tests for canonical host-context injection, and runtime tests that simulate lock/unlock transitions, locked fallback selection, isolated lock navigation, and full pre-lock restoration. [VERIFIED: packages/cli/src/config/loader.test.ts, packages/cli/src/deck/runtime.test.ts, .planning/ROADMAP.md] [HIGH]
