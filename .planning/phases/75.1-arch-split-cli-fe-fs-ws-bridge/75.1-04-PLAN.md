# Plan 75.1-04: Emulator mode + complete tracer bullet

## Goal

Add emulation mode end-to-end. The Frontend Server renders the device selector + emulator panels; the iframe is a pure canvas; emulated button presses flow through the same WS bridge as real hardware. Final verification: both modes work on the same config.

## Context

Plans 01-03 proved the architecture for real mode. The diagram explicitly shows emulation mode as a separate flow: the user opens the Frontend Server URL in their browser, the Frontend Server serves the emulator panels (device selector + mouse-emulation code), and an iframe loads the React deck app. This plan completes the architecture.

### Task 2: Mouse → button-action translation

<files>
- packages/cli/frontend/src/emulator/mouse-to-button.ts (new)
- packages/cli/frontend/src/emulator/IframeCanvas.tsx (modify)
- packages/cli/frontend/src/ws-client.ts (modify — expose send())
</files>

<action>
1. Write `mouse-to-button.ts`:
   ```ts
   export interface DeviceLayout { keyWidth: number; keyHeight: number; cols: number; rows: number; }
   export function attachMouseEmulation(opts: {
     overlayEl: HTMLElement;
     iframeEl: HTMLIFrameElement;
     device: DeviceLayout;
     send: (msg: Message) => void;
   }): () => void;  // returns detach
   ```
   Implementation:
   - Listen for `mousedown` / `mouseup` on `overlayEl` (a transparent div over the iframe).
   - On event, get click coords relative to `overlayEl`. Subtract the iframe's `getBoundingClientRect()` offset.
   - Compute `col = Math.floor(clickX / keyWidth)`, `row = Math.floor(clickY / keyHeight)`.
   - Compute `keyIndex = row * cols + col`. Skip if out of bounds.
   - Call `send({ type: 'button-action', keyIndex, action: 'down' | 'up', at: Date.now() })`.
   - Detach removes the listeners.
2. Modify `IframeCanvas.tsx` to call `attachMouseEmulation` on mount, detach on unmount.
3. Modify `ws-client.ts` to expose `send()` (currently only `onMessage` and `onConnection` are exposed).
</action>

<verify>
- User clicks on a button in the iframe overlay → `button-action` message is sent over WS → CLI logs it.
- User drags across multiple buttons → multiple `button-action` messages fire in order.
- The iframe itself doesn't receive the mouse events (the overlay div catches them).
</verify>

<done>
Mouse clicks over the deck iframe are translated to WS `button-action` messages. The iframe stays a pure canvas.
</done>

## Verification

- `pnpm start` (real mode) and `pnpm emulate` (emulation mode) both work end-to-end on the same config.
- Date-time addon renders identically in both modes.
- Mouse → button-action translation works.
- WS bridge logs all messages consistently across modes.
- No new test failures vs. baseline.
- Architecture summary doc captures the full system.

## Risks

- **Emulator panels compete with the iframe for input**: the overlay div catches mouse events before the iframe; the iframe never sees them. Mitigation: explicitly stop event propagation in `mouse-to-button.ts`.
- **Real-mode and emulation-mode paths diverge over time**: developers add behavior to one and forget the other. Mitigation: shared helper for the WS-bridge-to-renderer contract; both modes consume the same `DeckConfigMessage` payload.
- **Headless Chromium in real mode + user browser in emulation mode behave differently**: a feature works in one and breaks in the other. Mitigation: Playwright e2e test that runs both modes and asserts equivalent output.

## Demo

`pnpm start` → real Stream Deck shows the date-time button. `pnpm emulate` → user opens browser, sees the emulator panels + deck iframe. Click button → CLI logs the action, sends state update, deck updates. Both modes proven end-to-end on the same config.
