# Phase 6 Plan 3: Overlay Auto-Resume on Unlock + Nav Stack Restore

## Goal

Lock → unlock preserves user context: a Spotify overlay that was showing pre-lock reappears post-lock (if Spotify is still the active window), and the user's position inside that overlay's nav stack is intact. Regular deck restoration happens regardless (already in Plan 1). The folder-escape path is explicitly NOT auto-restored.

## Must-Haves

- `preLockActiveDeckId` and `preLockOverlayDeckId` snapshots are taken at lock-entry time (Plan 1 wires the snapshot, Plan 3 wires the resume logic).
- On unlock, the runtime restores the pre-lock state in this order:
  1. Clear `lockActive` (Plan 1).
  2. If `preLockOverlayDeckId !== null` AND the overlay's trigger still matches the current active app (`computeOverlayFor(currentSnapshot) === preLockOverlayDeckId`): call `setOverlay(preLockOverlayDeckId, { source: 'autoShow' })` — overlay's nav stack is preserved (Plan 5 design — `overlayNavStacks` already persists across dismiss/reactivate).
  3. Else if `preLockOverlayDeckId !== null` AND trigger no longer matches: clear `preLockOverlayDeckId`, call `navigateToDeck(preLockActiveDeckId ?? mainDeck.id, { addToHistory: false })`.
  4. Else (no overlay was active): call `navigateToDeck(preLockActiveDeckId ?? mainDeck.id, { addToHistory: false })`.
- If the unlock follows a folder-escape (`lockActive` was already `false`), the resume is a no-op — Plan 2 Task 2.4 already guards this.
- Edge case: lock entered while an overlay is active, lock-entered event suspends (`overlayDeckId` stays set in closure but `getActiveDeckId` returns `'lock:deck'`). On unlock, `preLockOverlayDeckId` is the previously-active overlay; resume uses `setOverlay` which restores the overlay's nav stack from `overlayNavStacks`.
- Edge case: lock entered with a non-overlay transient deck (e.g. paginated sub-page) — `preLockActiveDeckId` is the transient id, restore uses `navigateToDeck(..., { addToHistory: false })` which sets `transientDeckId` correctly.
- Tests:
  - Overlay active → OS locks → OS unlocks + trigger still matches → overlay resumes; nav stack restored.
  - Overlay active → OS locks → OS unlocks + trigger no longer matches → overlay dismissed; regular deck restored.
  - No overlay → OS locks → OS unlocks → regular deck restored.
  - Transient deck → OS locks → OS unlocks → transient deck restored (verify `getActiveDeckId` returns the transient id).
  - Lock → folder-escape → OS unlocks → no auto-restore (escape is sticky).
  - Lock → OS locks again (still locked) → snapshots are refreshed, no double-resume.

## Task 3.2: Implement `restoreFromLockSnapshot`

- **Files:** `packages/cli/src/deck/runtime.ts`, `packages/cli/src/deck/__tests__/overlay-lock-resume.test.ts`
- **Action:** Implement:
  ```ts
  const restoreFromLockSnapshot = (snapshot: ActiveAppSnapshot | null): void => {
    if (preLockOverlayDeckId !== null) {
      const stillMatches = snapshot !== null
        ? computeOverlayFor(snapshot) === preLockOverlayDeckId
        : false
      if (stillMatches) {
        // Overlay auto-resumes; nav stack is preserved by overlayNavStacks
        setOverlay(preLockOverlayDeckId, { source: 'autoShow' })
        preLockActiveDeckId = null
        preLockOverlayDeckId = null
        return
      }
      // Trigger no longer matches; fall through to regular restoration
      preLockOverlayDeckId = null
    }
    const restoreId = preLockActiveDeckId ?? mainDeck.id
    preLockActiveDeckId = null
    navigateToDeck(restoreId, { addToHistory: false })
  }
  ```
  Call this from the unlock branch of the session-subscribe callback.
