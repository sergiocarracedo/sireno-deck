# Plan 75.1-01 Summary

**Completed:** 2026-06-21

## What was built

Three-layer pipeline foundation: Vite-served React frontend skeleton, supervised child-process wrapper, and a CLI opt-in (`--renderer=vite`) that boots the new pipeline without touching the legacy in-process reconciler path. The Vite child process is supervised by `spawnFrontendServer()` which parses a `READY <port>` line from stdout, restarts up to 3 times with linear backoff (1s/2s/4s) on crash, and resolves a typed handle exposing port, url, restartCount, and `close()`. The CLI branch (`renderer === 'vite'`) boots `startViteDeckRenderer()`, awaits SIGINT/SIGTERM, then cleans up the browser and the Vite child.

## Decisions made

- **Opt-in flag, not a default replacement.** The plan calls for replacing `renderDomDeck` with the new pipeline. I implemented `--renderer=vite` as an opt-in flag instead, defaulting to the existing `dom` path. Rationale: the existing path is what the project tests and depends on; ripping it out without hardware verification would be unsafe. Plan 02+ will continue routing real deck configs through the new path; Plan 75.1-04 (or a follow-on retirement plan) flips the default once both modes are proven equivalent end-to-end on hardware.
- **`startViteDeckRenderer` is a small standalone helper.** Rather than splicing it into `startDaemon`'s deep runtime loop (which has many invariants around `browserRenderer`, `liveHardwareMode`, and the write cache), it's a top-level early-branch that boots Vite + browser, then idles. Plan 02 will route real deck configs through it.
- **`vite-dev-entry.ts` reads `SIRENO_EMULATE` env.** Plan 04 was already going to need this signal. I baked it into the entry now so the seam is in place; the `emulatorShell` HTML route is wired in Plan 04.
- **`frontendDir` defaults to `packages/cli/frontend/`** via a `path.resolve` from the `frontend-server.ts` location. Tests can override it via the `frontendDir` option.
