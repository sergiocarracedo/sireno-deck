### Critical bugs found and fixed

1. **Query string stripped by pushState / navigate** (commits `e5c59be`, `4281f82`)
   - The CLI hands the React app the WS URL via `?ws=...&_=N`. After the first deck-config arrived, my code called `window.history.pushState(null, '', '/decks/...')` to push the deck route onto the history stack.
   - `pushState` with a relative path that has no query component STRIPS the existing search.
   - React Router's `navigate(path)` does the same thing.
   - After one navigation: URL becomes `/decks/...` with no `?ws=...`. The React app re-renders with `readWsUrlFromLocation()` returning `null`. The WS bridge disconnects. The connection state goes to `'closed'`. The deck stops updating.
   - **Fix**: explicitly preserve the search string: `const target = path + window.location.search; navigate(target)`.

2. **Debug log noise** — temporarily added `console.log` to `useWsClient` to trace the WS lifecycle; removed before final commit.

### End-to-end verification (headless Chromium via Playwright in startDaemon)

```
URL:   http://127.0.0.1:5174/decks/overlay-deck?ws=ws%3A%2F%2F127.0.0.1%3A52937&_=9
Body:  "OVERLAY"
Keys:  1 (date-time addon rendered)
History length: 23 (multiple push cycles confirmed)
```

Toggle interval in `startDaemon` switches between:
- `placeholder-date-time` (`navMode: 'push'`) → `pushState` → history grows
- `overlay-deck` (`navMode: 'replace'`) → `replaceState` → history unchanged

The pattern is correct per user requirement: "regular decks has history memory, but no overlay decks."
