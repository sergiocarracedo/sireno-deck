# Phase 6 Plan 2: User-Defined Lock Deck + Gesture Suppression with Folder Escape

## Goal

With `lock.buttons` configured, OS-lock surfaces the user's custom buttons. Tapping a non-folder button does nothing (silent drop). Tapping a folder-nav button (e.g. `core:change-deck` with a `deck` config, or a button whose `actions.tap` is a `navigate://<deckId>` dispatch) is the escape hatch: it sets `lockActive = false`, and the existing dispatch path navigates normally — system buttons re-inject on the destination deck.

## Must-Haves

- `lock.buttons` accepts the standard `ButtonDefSchema` shape (full spec — `type`, `config`, `actions`, etc.).
- `buildUserLockDeck(buttons: ButtonDef[]): RuntimeDeck` returns a deck `{ id: 'lock:deck', name: 'Locked', buttons: <with positions preserved> }`.
- `getActiveDeck()` returns the user-built deck when `lockConfig.buttons.length > 0`, else the default 3-button time deck (Plan 1).
- `invokeAction` (in `runtime.ts`) has a lock-mode pre-check at the top:
  - If `lockActive && deck.id === 'lock:deck'` and the resolved `userAction` (from `actions.tap/dbltap/hold`) starts with `navigate://`, set `lockActive = false` and **continue** (do not return) — the existing dispatch path runs.
  - Else if `lockActive && deck.id === 'lock:deck'` and no escape detected: `return` early — no `dispatch`, no `showTemporaryError`, no log noise.
  - Detection covers `navigate://<deckId>` (existing folder-nav dispatch format — confirm exact prefix in `dispatchMacro` or wherever `navigate://` is registered).
- After folder escape, `lockActive` stays `false` until the next OS `state === 'locked'` event — the unlock handler must not re-clear a lock that was already cleared (idempotent: only set `lockActive = false` if currently `true` and `preLock*` snapshots are no longer relevant).
- The folder-escape path runs the existing `getMethods().dispatch(userAction)` — the destination deck gets its system buttons re-injected on the next `injectSystemButtons` pass because `lockActive` is now `false`.
- Tests cover: user-defined lock deck renders from config; non-folder `actions.tap: 'paste://test'` is dropped silently; folder `actions.tap: 'navigate://system'` triggers escape + navigate + sets `lockActive=false`; no `dispatch` call for non-folder actions; post-escape `getActiveDeckId()` returns the destination deck.

## Task 2.3: Lock-mode pre-check in gesture router

- **Files:** `packages/cli/src/deck/runtime.ts`, `packages/cli/src/deck/__tests__/lock-deck.test.ts`
- **Action:** At the top of `invokeAction(buttonId, gesture)` (after `findButton` returns), add:
  ```ts
  if (lockActive && found.deckId === 'lock:deck') {
    const escape = resolveLockEscapeAction(found.button, gesture)
    if (escape !== null) {
      lockActive = false
      pubSub.publish('runtime:lock-mode', { active: false, reason: 'escape' })
      // fall through — the normal dispatch path runs below with the escape action
    } else {
      logger.debug({ buttonId, gesture }, 'lock-mode: gesture suppressed')
      return
    }
  }
  ```
  Where `resolveLockEscapeAction` reads `actions[gesture]` (mapped from `GestureKind` → `tap`/`dbltap`/`hold`) and returns it only if it satisfies `isLockFolderEscape`.
- The pre-check runs BEFORE `getMethods().dispatch(userAction)` and BEFORE `checkRequirement` — so a locked user-button folder escape skips the capability check (matching regular navigation flow).
- **Verify:** Unit tests: (a) tap on `core:action` button → no dispatch, no error, returns void; (b) tap on `core:change-deck` button → `dispatch` called with `navigate://system`, `lockActive` is `false`, `getActiveDeckId()` returns `'system'`; (c) dbl-tap and hold also work for the escape gesture.
