# Plan 11-01: Ship The Canonical Host Context End-To-End

<objective>
Land the first complete Phase 11 tracer bullet by introducing the canonical host/session contract where users can actually see and use it: one normalized host context powers addon input, config templating, and action/status execution through the live runtime. A completed plan should let a committed Phase 11 fixture render host-aware output and exercise both host-aware action and status-bearing execution without inventing a second host-data path or a fake demo-only surface.
</objective>

## Tasks

<task id="11-01-01">
<title>Introduce the canonical host-context provider and add it to the addon runtime contract</title>
<files>
- packages/cli/src/system/host-context.ts
- packages/cli/src/addon/api.ts
- packages/cli/src/deck/runtime.ts
- packages/cli/src/deck/runtime.test.ts
</files>
<action>
Add a dedicated `packages/cli/src/system/host-context.ts` module that defines the canonical normalized host-context TypeScript types and the first provider implementation. Normalize OS fields to the user-approved `type`, `variant`, and `version` shape by reusing `systeminformation` for static OS information, and initialize session info with the approved `capability` plus `state` contract, using `unknown` where lock detection has not been wired yet. Extend `CreateAddonButtonInstanceOptions` in `packages/cli/src/addon/api.ts` to carry this host context as first-class input. Thread the same object through `packages/cli/src/deck/runtime.ts` when creating addon instances, and update `packages/cli/src/deck/runtime.test.ts` with focused assertions that runtime-created buttons receive the canonical host context unchanged.
</action>
<verify>
Run `pnpm --filter sireno-deck-cli exec vitest run src/deck/runtime.test.ts`.
</verify>
<done>
The runtime owns one canonical host-context object and passes it directly into addon instance creation without inventing a parallel getter-based API.
</done>
</task>
