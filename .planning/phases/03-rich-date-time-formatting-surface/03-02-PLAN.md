# Plan 03-02: Integrate Date-Time Through The Shared Markup Seam

<objective>
Land the second Phase 3 tracer bullet by wiring the built-in date-time button through the new shared rich-text seam without losing Day.js token formatting or corrupting markup literals. This slice matters because the hardest real integration risk in Phase 3 is not the parser itself, but the handoff between Day.js token expansion and the shared `Text` parser when the same `format` string now contains both date tokens and rich-markup syntax.
</objective>

## Tasks

<task id="03-02-01">
<title>Preserve markup literals around Day.js token expansion and route date-time through shared rich `Text`</title>
<files>
- packages/cli/src/builtin-addons/date-time/format.ts
- packages/cli/src/builtin-addons/date-time/buttons/date-time.tsx
- packages/cli/src/builtin-addons/date-time/index.test.ts
</files>
<action>
Refactor the date-time formatting seam so the button keeps its single `format` field and still uses Day.js as the token engine, but markup literals survive token expansion intact before the resulting string reaches shared `Text`. Use one explicit preservation strategy rather than a naive raw `dayjs(...).format(config.format)` pass over strings containing markup-like tags. Then keep the date-time button itself narrow: it should still render one shared `Text`, now relying on the shared parser from Plan 03-01 instead of a widget-local rich renderer. Update focused date-time tests so they prove nested rich markup, literal fallback, and the current single-field config contract through the real mounted date-time path.
</action>
<verify>

</verify>
<done>

</done>
</task>
