# Plan 72-01: Deck icon field + OverlayToggleButton render

## Context

Overlay decks declared in user config can carry metadata that should be surfaced in the UI. The `icon` field is the most natural one — it tells the runtime what visual badge to render on the overlay-toggle / split-action buttons. Today, the field is silently dropped at `CoreDeckConfigSchema.strict()` even though the raw YAML is accepted by `RawDeckSchema.passthrough()`. The `OverlayToggleButton` falls back to extracting a leading emoji from the deck name (and then to `layout-grid` + "Show App" if no emoji), which works for some decks (e.g. "🎵 Spotify" → 🎵) but is unusable for decks whose name starts with a regular character ("Chrome" → nothing).

The user has been clear (Phase 72 discuss): the `icon` field follows the same convention as the action button icon field (`icon://<name>`, `brand://<name>`, `./<path>.svg`, `addon://...`). The existing `resolveIconSpec` utility in `packages/cli/src/ui/Icon.tsx:95` already handles all four formats and is used by `change-deck`, `action`, and `toggle` buttons. **No new utility is needed** — BUG-04 is a schema addition + a single render update.

The fallback chain in `OverlayToggleButton` is extended, not replaced: configured `icon` → first emoji of deck name (unchanged) → uppercase first character of deck name (NEW) → `layout-grid` (unchanged, kept for nameless decks).

## Tasks

### Task 1: Add `icon` field to the deck schema AND carry it through every loader seam

**file:** `packages/cli/src/core/schemas.ts`
**action:** The `icon` field must survive from `validateConfig` input to the runtime `decks[deckKey]` builder. The plan-checker flagged that `RawDeckSchema.passthrough()` keeps the field on the raw parse, but `CoreDeckConfigSchema.strict()` plus 3 downstream seams drop it. The field must be added in **all** of these places:

1. `CoreDeckConfigSchema` definition (lines 213-219) — add `icon: z.string().min(1).optional()` between `autoShow` and `background`.
2. `DeckConfig` interface (lines 190-203) — add `icon?: string` so the type system allows the field to flow to runtime.
3. `expandDecks` non-addon call site (lines 470-471) — add `...(deck.icon !== undefined ? { icon: deck.icon } : {})` (mirrors the `background` pattern).
4. `expandDecks` addon call site (lines 509-511) — same pattern.
5. Final `decks[deckKey]` builder (lines 654-691) — add `...(bootstrap.decks[deckKey]?.icon !== undefined ? { icon: bootstrap.decks[deckKey]?.icon } : {})` for every persisted field, mirroring how `background` is propagated.

Use `grep` to find all `(bootstrap.decks[deckKey]?` occurrences in the file and follow the same `(value !== undefined ? { value } : {})` discipline for `icon`.

**verify:** Run the schema round-trip test from Task 3 (the only reliable end-to-end check).
**done:** `validateConfig({ decks: { main: { buttons: [], icon: "icon://app-window" } } })` succeeds and `runtimeDecks.main.icon === "icon://app-window"` (verified via the runtime's `decks[deckKey]` builder).

### Task 2: Update `OverlayToggleButton` to render the configured icon

**file:** `packages/cli/src/deck/system-buttons/OverlayToggleButton.tsx`
**action:** Add `import { resolveIconSpec } from '@/ui/Icon'`. Update the badge icon resolution in the render to:
1. If `activeOverlayDeck.icon` is a non-empty string, use `resolveIconSpec(activeOverlayDeck.icon)` as the badge.
2. Else, attempt first-emoji extraction (existing logic at `^\p{Extended_Pictographic}`).
3. Else, if the deck has a non-empty name, use the uppercase first character of the name as a single-character `Icon name={...}` fallback.
4. Else, fall back to `layout-grid` (existing fallback for nameless decks).

The order matters: configured `icon` takes priority, then emoji, then name initial, then placeholder.
**verify:** Visual inspection of the render — when `activeOverlayDeck.icon` is set, `resolveIconSpec` is called and the result is passed to `<Icon>`.
**done:** `OverlayToggleButton` uses the new fallback chain and prioritizes the configured `icon`.
