# Phase 03 Plan 02 — Action Executor + Deck Runtime

## Context

Plan 01 gave us the four core primitives. This plan builds the orchestration layer that sits between the runtime and the addons:

1. **Action executor** — runs shell commands via `execa` with `{{ host.* }}` placeholder interpolation.
2. **Host context** — typed access to host info (`hostname`, `platform`, `userInfo`, `arch`).
3. **Deck methods** — the `methods.*` surface that addon button contexts receive: `runCommand`, `keyMacro`, `pasteText`, `navigateToDeck`, `goBack`, `getActiveDeckId`, `invalidate`, `publish`, `subscribe`. Phase 07 will wire real OS providers; for now `keyMacro` and `pasteText` throw `NotImplementedError`.
4. **System back injection** — computes whether slot `n-1` should be replaced by a system button (`back`, `settings-entry`, or `overlay-toggle`) based on deck type + nav state.
5. **Deck runtime** — holds nav stack, active deck, overlay state, gesture state per button, dispatches gestures to button handlers.

We do not yet load addons in this plan — that's Plan 03. The runtime works against a fixture deck registry so the unit tests are self-contained.

## Notes for executor

- `execa` already in deps. No new dep needed.
- Runtime is decoupled from `@/addon` — accepts `RuntimeDeck[]` and handler maps externally.
- `dispatchGesture` accepts the 3-value union (tap/dbl-tap/hold) and dispatches to the corresponding handler. If only `onTap` is registered, dbl-tap and hold are no-ops (logger warn).
- `keyMacro`/`pasteText` throw — explicit `NotImplementedError` so Phase 07 can find them with a grep.
- DO NOT add comments unless user asks.
