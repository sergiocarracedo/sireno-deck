# Phase 03 Plan 03 — Built-in Addons + Full Config Validation

## Context

Plan 01 built core primitives. Plan 02 built the runtime + executor + methods + system back injection. This plan wires the three built-in addons (`core-buttons`, `internal-settings`, `session`) into the addon registry, defines their button types and programmatic decks (`settings` + `session:locked`), and extends config validation to run per-button `configSchema` checks (the second half of two-phase validation) plus reject `internal: true` buttons when found in user config.

This is the **tracer bullet** for Phase 03. After this plan completes, the following end-to-end user behavior works:

1. User writes `config.yml` with `decks.main` containing `core:change-deck` and `core:action` buttons.
2. CLI loads the config, the line-aware YAML loader parses it.
3. The full config validation runs: `internal: true` buttons in user config → rejected; per-button `configSchema` (zod) parsed against `config`.
4. Built-in addons register themselves via `registerBuiltins(registry)` and the addon registry indexes their button types.
5. The runtime instantiates with the deck + registered buttons.
6. On a `tap` gesture dispatched for `core:action`, the executor runs the configured command and the result is captured.
7. On a `tap` gesture for `core:change-deck`, the runtime navigates to the configured deck.
8. `internal-settings` addon's `createDecks` returns a `settings` deck with brightness + theme + about buttons.
9. `session` addon's `createDecks` returns a `session:locked` deck with the current time on each button.

## Notes for executor

- Built-in addons live in `packages/cli/src/builtin-addons/` (not in `dist/`). Each addon is a separate folder with an `index.ts` entry. Files per button, not per type.
- `core:settings-*` and `session:time` are `internal: true` — they will be rejected by full validation if used in user config.
- `session:time` uses `.tsx` extension (not `.ts`) so we don't have to rename it later when adding JSX.
- `runtime.dispatchGesture` requires handlers to be registered via `runtime.registerButtonHandler(buttonId, { onTap, onDblTap, onHold })`. In the integration test, handlers come from the addons — wire them manually for now (Phase 04 will automate this via `loadAddons → mount → register`).
- For the integration test, write a fixture config to a temp dir using `tmpdir()` + `os.tmpdir()`, then load via `loadConfig({ configPath: tmpFile })`.
- `execa` output for `echo integration` is `'integration\n'` (the trailing newline from echo). Test asserts exactly that.
- DO NOT add comments unless user asks.
