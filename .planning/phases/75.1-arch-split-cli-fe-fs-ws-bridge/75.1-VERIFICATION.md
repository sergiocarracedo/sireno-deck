## Architectural decisions made during execution

1. **Stable WS bridge port (52937)** as default; overridable via `SIRENO_WS_PORT` env or `opts.port`. Original intent was full auto-select per session; pin keeps tests reproducible. User feedback: "ports can change on each session" — this is a soft default, not a lock.

2. **Static imports for built-in addon frontends** (per user's choice of option 2). `BUILTIN_ADDON_FRONTENDS = { 'date-time': DateTimeFrontend }` in `Deck.tsx`. Vite bundles them at build time. Dynamic loading of raw-source addons deferred.

3. **`@/` Vite alias points at `packages/cli/src`** (not `packages/cli/frontend/src`) so addon frontend files can use `@/ui`, `@/themes/utils/cn`, `@/render/protocol` etc. — matches their actual location.

4. **Direct relative imports in date-time/frontend.tsx** (`../../ui/Text` not `@/ui`) — the `@/ui` barrel transitively loads `LabelValueListSurface → Icon → addon/api → node:path`. Direct imports avoid that chain in browser builds.

5. **History push/replace preserves query string**: `useNavigate(path + window.location.search)`. Without this, the WS bridge URL `?ws=...` is stripped on first navigation and the bridge disconnects.

6. **No new `overlay` schema field**: `navMode` is derived from existing `process_names + autoShow === false` semantics in the CLI when sending real deck-configs.

7. **Emulator URL injection via Vite `transformIndexHtml` plugin** (Plan 05): the emulator Vite child reads `SIRENO_DECK_URL`/`SIRENO_WS_URL`/`SIRENO_KEY_COUNT` from env (inherited from the CLI parent via `vite-server.ts:75`) and injects `<script>window.__SIRENO__ = {deckUrl, wsUrl, keyCount};</script>` into `index.html`. The page URL stays clean. Chose env-injection over a WS "hello" handshake because URLs are stable for the process lifetime and the page can render synchronously without waiting for a WS roundtrip. The deck iframe URL inside `IframeCanvas.tsx` STILL has `?ws=...` because the deck page reads it via `App.tsx:readWsUrlFromLocation()` — different concern, intentionally untouched.

## Deferred to follow-on phases

1. **Real-hardware verification** — no Stream Deck device in this environment. All UI checks are via headless Chromium.

2. **`dom-host/` retirement** — touched by 51+ files (100+ references including test fixtures). Needs its own dedicated phase. The dom-host retirement was a CONTEXT decision but the runtime.ts rewrite is a separate multi-day surgery.

3. **Plan 01-04 hardware back button integration** — the WS `button-action` message handler exists on the CLI side (logs it) but isn't yet wired to the navigation logic (pop history, dismiss overlay). Currently only the dev toggle interval exercises the router.

4. **Dynamic loading of raw-source addons** — option 2 chose static imports for built-ins. Raw-source addon frontends will need either a Vite plugin (resolveId hook) or runtime copying (CLI → Vite root) to be supported.
