# Plan 72-02: 2-line SplitActionSurface variant for overlay summon

## Context

The base deck's reserved back position is the entry point for overlay interactions. Today, when a base deck has a `pendingOverlayDeck` configured (the overlay is defined but not yet shown because `autoShow: false` or the active app doesn't currently match), the dispatcher at `packages/cli/src/deck/system-buttons/system-buttons.ts` injects a `SPLIT_ACTION_TYPE` button. The render at `runtime.ts:1098-1114` shows a `MainLabelSurface` with `send-to-back` icon + the deck name in the secondary slot. The user wants the secondary slot to show the **overlay deck's icon** (from BUG-04's new schema field) instead — and the action wired to `summonOverlay`.

The 2xTap action is largely already wired: the existing `onDblTapOverride` passed to `createSystemBackHandlers` (runtime.ts:1083-1095) calls `summonOverlay(summonableDeckId)` when an active app matches. The 72-02 work focuses on:
1. **Visual**: replace the `send-to-back` icon in the secondary slot with the overlay deck's icon (via `resolveIconSpec(deck.icon)` from 72-01).
2. **Action verification**: confirm the existing `onDblTapOverride` logic is correct for the summon-only semantics the user described. If it needs to be simplified (e.g. always summon `pendingOverlayDeck.id` instead of going through `findSummonableActiveAppDeckFor`), update it.
3. **Tests**: add a runtime test that 2xTap on the base deck's split-action button (when `pendingOverlayDeck` is set) calls `summonOverlay`.

The user explicitly chose to reuse `SplitActionSurface` as-is (no new visual variant). The 2xTap indicator chip is automatic.
