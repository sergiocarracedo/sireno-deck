# Phase 6 Plan 1: Default Time Lock Deck Activates on OS Lock

## Goal

Lock the OS → a 3-button HH:MM deck appears as the active deck with no n-1 system buttons; unlock → the main deck is restored. After this plan, the minimum-viable lock experience works without any user config (`lock:` block empty/absent → default time deck). User-defined `lock.buttons` and gesture suppression land in Plan 2; overlay auto-resume lands in Plan 3.

## Must-Haves

- `lock: z.object({ buttons: z.array(ButtonDefSchema).optional() }).strict().optional()` accepted at the root of `RawConfigSchema`.
- `session.locked_deck` schema field removed (orphaned since Phase 5, replaced by `lock:`).
- Runtime holds closure-local `lockActive: boolean`, `preLockActiveDeckId: string | null`, `preLockOverlayDeckId: string | null`.
- `getActiveDeckId()` returns `'lock:deck'` when `lockActive` — strictly overrides regular and overlay nav stacks.
- `getActiveDeck()` synthesizes a default `lock:deck` with 3 buttons (`date-time:locked-time-tile`, slots `'hour'` / `'separator'` / `'minute'`) when `config.lock?.buttons` is empty/absent.
- `computeSystemButtonForSlotN1` returns `null` when `lockActive === true`; `injectSystemButtons` then produces no n-1 button.
- `Runtime` exposes `setSessionProvider(provider: SessionProvider)` and `isLockActive(): boolean`.
- `createRuntime` subscribes to the session provider on `setSessionProvider` and toggles `lockActive` on `state === 'locked'` / `state === 'unlocked'` transitions.
- On lock entry: snapshot `preLockActiveDeckId = getActiveDeckId()` and `preLockOverlayDeckId = overlayDeckId`.
- On unlock: clear `lockActive`; restore `preLockActiveDeckId` via `navigateToDeck(..., { addToHistory: false })`. Overlay resume is Plan 3.
- `startSystemProviders` in `run.ts` wires `session` into `runtime.setSessionProvider(session)` (currently dangling).
- `pnpm typecheck` passes; new tests pass; the existing `session:locked` 5-button broken deck is removed (its `NullButton` frontend is replaced by the runtime-built default).
- No protocol message changes — the lock deck flows through the existing `deck-config` message like any other deck.
