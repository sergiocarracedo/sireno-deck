# Plan 75.1-02: WebSocket bridge + deck-config round-trip

## Goal

Add the WebSocket bridge between the CLI and the React app. Push a real deck config (the date-time builtin as the tracer bullet) through the bridge and prove the React app renders it correctly. End-to-end on real hardware.

## Context

Plan 01 proved the three-layer plumbing with a hardcoded placeholder. This plan replaces the placeholder with the real architecture: the CLI sends actual deck configs over WS, the React app renders addon surfaces from those configs, and the screenshot matches what the old in-process reconciler would have produced.

## Tasks

### Task 1: Define the WS message protocol

<files>
- packages/cli/src/render/protocol.ts (new)
</files>

<action>
1. Create `packages/cli/src/render/protocol.ts` with discriminated-union zod schemas and inferred TypeScript types:
   - `protocolVersion: 1` (literal) on every message.
   - `DeckConfigMessage`: `{ protocolVersion: 1, type: 'deck-config', deckId: string, surfaces: Record<string, SurfaceSpec> }`. `SurfaceSpec` references addon frontend entries by path.
   - `StateMessage`: `{ protocolVersion: 1, type: 'state', payload: Record<string, unknown> }` (generic state bag — initial scope is empty).
   - `ButtonConfigMessage`: `{ protocolVersion: 1, type: 'button-config', keyIndex: number, surface: SurfaceSpec | null }` (per-key update — used for invalidation later).
   - `ButtonActionMessage`: `{ protocolVersion: 1, type: 'button-action', keyIndex: number, action: 'down' | 'up', at: number }` (from runner to CLI).
   - `SnapshotMessage`: `{ protocolVersion: 1, type: 'snapshot', png: ArrayBuffer }` (only used in emulation mode where the iframe sends a screenshot of itself; in real mode the snapshot stays inside the headless browser and is captured directly by Playwright).
   - `MethodCallMessage`: `{ protocolVersion: 1, type: 'method-call', method: 'pasteText' | 'keyMacro' | ..., args: unknown[], callId: string }` (runner asks CLI to execute a backend method).
   - `MethodCallResultMessage`: `{ protocolVersion: 1, type: 'method-call-result', callId: string, ok: boolean, result?: unknown, error?: string }` (CLI replies).
2. Export a `parseMessage(raw: string): Message` function that validates with the zod schemas and throws on protocol violation.
3. Export a `serializeMessage(msg: Message): string` function.
</action>

<verify>
- Unit tests (`packages/cli/src/render/__tests__/protocol.test.ts`):
  - Round-trip each message type: serialize → parse → deep-equal.
  - Reject messages with wrong `protocolVersion`.
  - Reject messages with missing required fields.
  - Reject messages with extra unknown fields (strict zod mode).
</verify>

<done>
WS message protocol is documented, validated, and round-trippable. Versioned independently from `SIRENO_ADDON_API_VERSION`.
</done>

### Task 2: CLI-side WS bridge server

<files>
- packages/cli/src/render/ws-bridge.ts (new)
</files>

<action>
1. Create `packages/cli/src/render/ws-bridge.ts`:
   ```ts
   import { WebSocketServer } from 'ws';
   export interface WsBridgeHandle {
     port: number;
     send(msg: Message): void;          // to first connected client
     broadcast(msg: Message): void;     // to all connected clients
     onMessage(handler: (msg: Message) => void): () => void;
     onConnection(handler: (connected: boolean) => void): () => void;
     close(): Promise<void>;
   }
   export function createWsBridge(opts: {
     logger: pino.Logger;
     port?: number;  // default 0 = auto-select
   }): Promise<WsBridgeHandle>;
   ```
2. Implementation:
   - `new WebSocketServer({ port: opts.port ?? 0, host: '127.0.0.1' })`. Resolve with the bound port from `server.address().port`.
   - Log `WS bridge ready at ws://127.0.0.1:<port>`.
   - Track connected clients in a `Set<WebSocket>`. `broadcast` iterates and `ws.send(JSON.stringify(msg))` to each. Drop clients whose `readyState !== OPEN`.
   - Inbound messages: `JSON.parse` → `parseMessage` → dispatch to `onMessage` handlers. Log and drop on parse failure.
   - `close()` shuts the server gracefully.
3. Add `ws` as a dependency in `packages/cli/package.json`.
</action>

<verify>
- Unit tests (`packages/cli/src/render/__tests__/ws-bridge.test.ts`):
  - `createWsBridge()` resolves with an auto-selected port.
  - Open a WS client, send a message, assert the server's `onMessage` handler receives it.
  - `broadcast()` sends to all connected clients.
  - `close()` rejects further sends and waits for in-flight messages.
  - Invalid message (wrong protocolVersion) is logged and dropped, doesn't crash the server.
</verify>

<done>
WS bridge server lives in CLI. Unit-tested in isolation. localhost-only, no auth.
</done>

### Task 3a: CLI-side addon path resolver

<files>
- packages/cli/src/render/addon-paths.ts (new)
</files>

<action>
1. Create `packages/cli/src/render/addon-paths.ts`:
   ```ts
   export interface ResolvedAddonPath {
     addonName: string;
     frontendEntry: string;        // absolute filesystem path
   }
   export function resolveAddonFrontendPath(opts: {
     addonName: string;
     frontendEntry: string;        // e.g. './frontend' from manifest
     addonPackageRoot: string;     // e.g. packages/cli/src/builtin-addons/date-time
   }): ResolvedAddonPath;
   export function resolveRawAddonFrontendPath(opts: {
     addonName: string;
     frontendEntry: string;
     addonPackageRoot: string;
   }): ResolvedAddonPath;
   ```
2. Implementation:
   - Builtin addons: `path.resolve(addonPackageRoot, frontendEntry)` + resolve to `.tsx`/`.ts` extension if missing.
   - Raw-source addons: same, but warn if the resolved file is outside the addon's declared root (security check; matches the existing Phase 23 raw-source contract).
   - Return the absolute path; the frontend dynamic-imports this directly (Vite serves it from the CLI's working directory).
3. The CLI emits the resolved path in the `SurfaceSpec` payload — not the `addon://` URL scheme. The frontend never sees `addon://`; it always gets a path it can `import()`.
</action>

<verify>
- Unit tests (`packages/cli/src/render/__tests__/addon-paths.test.ts`):
  - Builtin addon: `./frontend` from `date-time` package root resolves to absolute path ending in `frontend.tsx`.
  - Missing extension: `./frontend` resolves to `./frontend.tsx` if `.tsx` exists; falls back to `.ts`.
  - Path traversal protection: raw-source addon with `frontend: '../../etc/passwd'` throws a clear error.
</verify>

<done>
CLI-side resolver converts addon `frontend` entries to absolute filesystem paths. Frontend receives paths it can `import()` directly. No custom URL scheme involved.
</done>

## Risks

- **WS client never connects**: CLI sits waiting forever. Mitigation: 5s timeout on the first `onConnection(true)`; after timeout, CLI logs fatal and exits. Subsequent reconnects use the existing 1s backoff.
- **Message schema drift**: a CLI and frontend built from different commits produce incompatible messages. Mitigation: `protocolVersion` is mandatory on every message; mismatch logs an error and drops the connection.
- **Date-time frontend crashes on certain configs**: error boundary in the React app surfaces it through `button-error` helper (existing pattern from Phase 5).
- **Vite restart doesn't reconnect cleanly**: the React app's WS client reconnects, but the WS bridge may have re-bound to a different port. Mitigation: WS bridge port is fixed for the lifetime of the CLI session; Vite restarts don't change it.
- **Addon `frontend` path resolution fails silently**: Task 3a's resolver converts relative paths to absolute filesystem paths; if it fails (missing file, traversal), the CLI must surface a clear error before the WS message is sent. Mitigation: `resolveAddonFrontendPath()` throws on missing or out-of-root paths; `start.ts` catches and renders the existing `button-error` helper on the affected key.
- **Test fixtures still import `renderDomDeck` from `dom-host/`**: Plan 01 Task 4 migrates `browser-renderer.test.ts`; this plan adds no new test fixtures but verifies the migrated tests still pass.
