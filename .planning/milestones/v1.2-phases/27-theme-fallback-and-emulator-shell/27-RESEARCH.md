## Common Pitfalls

### Deleting YAML themes halfway leaves a lying fallback seam
**What goes wrong:** The code removes some YAML-theme paths but keeps the core-owned `defaultButtonFrame` fallback or a hidden non-manifest codepath alive, so the repo still supports two theme systems while pretending it has one. [VERIFIED: packages/cli/src/config/theme.ts] [VERIFIED: packages/cli/src/render/dom-host.tsx]

**Why:** Today `getLocalThemeTarget(...)` can still classify a local theme path as `legacy_yaml`, and `resolveTheme(...)` still returns a parsed YAML theme with `buttonFrame: defaultButtonFrame`. That means resolution model and frame ownership are currently coupled to deprecated behavior. [VERIFIED: packages/cli/src/config/theme.ts]

**How to avoid:** Make one slice explicitly delete the `legacy_yaml` target/resolution path and re-anchor fallback ownership to the built-in default theme package. Update tests to stop asserting YAML-theme resolution and instead assert the manifest-backed default-theme fallback path. [VERIFIED: packages/cli/src/config/theme.test.ts] [VERIFIED: .planning/phases/27-theme-fallback-and-emulator-shell/27-CONTEXT.md]

### "Fixing" TSX runtime with scattered React imports hides the real seam
**What goes wrong:** Files keep or regain `import React from 'react'` only to satisfy a runtime edge, so tests pass while the actual TSX policy stays inconsistent and future runtime-authored `.tsx` files can fail again. [VERIFIED: packages/cli/src/render/dom-host.tsx] [VERIFIED: packages/cli/src/cli/commands/start.test.ts]

**Why:** The package tsconfig already opts into automatic JSX, but real execution still depends on how the CLI and `tsx` loader import TSX modules. Quick task 015 already exposed that Vitest success alone was not trustworthy proof for this seam. [VERIFIED: packages/cli/tsconfig.json] [VERIFIED: .planning/STATE.md] [CITED: https://www.typescriptlang.org/tsconfig/#jsx] [CITED: https://legacy.reactjs.org/blog/2020/09/22/introducing-the-new-jsx-transform.html]

**How to avoid:** Treat `packages/cli/src/cli/commands/start.test.ts`'s real `pnpm exec tsx --eval` assertion as the authoritative proof seam and make the implementation satisfy that test without ambient React globals or file-local compatibility imports where they are otherwise unused. [VERIFIED: packages/cli/src/cli/commands/start.test.ts]

### A missing watched file can look fixed if tests only exercise in-process reload
**What goes wrong:** Theme reload tests pass for runtime export changes, but a specific default-theme file like `ButtonFrame.tsx` falls out of `filePaths` or the real watcher graph and live reload silently stops working for that edit path. [VERIFIED: packages/cli/src/config/theme.test.ts] [VERIFIED: packages/cli/src/cli/commands/start.ts]

**Why:** The reload architecture is intentionally simple: one deduplicated file list, one watcher per path, recreated on reload. That simplicity is good, but it means any missing runtime dependency path becomes a truthfulness bug in the graph itself. Node's `fs.watch` also has platform caveats, which makes it even more important not to complicate the design unnecessarily. [VERIFIED: packages/cli/src/cli/commands/start.ts] [CITED: https://nodejs.org/api/fs.html#fswatchfilename-options-listener]

**How to avoid:** Prove the built-in default theme runtime graph still includes `themes/default/ButtonFrame.tsx` and use the existing `watchConfigFiles(...)` seam in tests instead of creating a separate watch mechanism. Keep verification anchored to actual returned `filePaths` and the real reload path. [VERIFIED: packages/cli/src/config/theme.test.ts] [VERIFIED: packages/cli/src/cli/commands/start.test.ts]

### Emulator chrome can accidentally keep bleeding into all browser-rendered surfaces
**What goes wrong:** The deck document remains visually polished everywhere because the shell gradients, inset shadows, and well highlights stay unconditional even after introducing an emulator-mode flag. [VERIFIED: packages/cli/src/render/dom-host.tsx]

**Why:** Phase 26 deliberately centralized shell styling in the shared document. That was the right move, but it also means one unconditional style block now affects both emulator and non-emulator browser renders. [VERIFIED: packages/cli/src/render/dom-host.tsx] [VERIFIED: .planning/phases/26-browser-deck-react-shell-polish/26-CONTEXT.md]

**How to avoid:** Keep one document seam but explicitly pass render intent into `renderDomDeck(...)`, then assert in `dom-host.test.tsx` that emulator mode retains the glass/chrome treatment while non-emulator renders keep layout and content without emulator-specific shell polish. [VERIFIED: packages/cli/src/render/dom-host.test.tsx] [VERIFIED: .planning/phases/27-theme-fallback-and-emulator-shell/27-CONTEXT.md]

## Existing Patterns In This Codebase

- **Manifest-backed theme runtime is already the real contract:** `packages/cli/src/config/theme.ts` already resolves package themes through `manifest.yml`, imports runtime modules with `tsx/esm/api` for `.ts/.tsx`, collects stylesheet assets, and returns a full watched `filePaths` graph. Phase 27 should deepen that seam, not add another one. [VERIFIED: packages/cli/src/config/theme.ts]
- **The built-in default theme already exports the fallback-worthy frame:** `packages/cli/src/themes/default/index.ts` exports `buttonFrame = ButtonFrame` from `packages/cli/src/themes/default/ButtonFrame.tsx`, so the natural fallback source already exists in the shipped theme runtime graph. [VERIFIED: packages/cli/src/themes/default/index.ts] [VERIFIED: packages/cli/src/themes/default/ButtonFrame.tsx]
- **One watched file graph already drives reload:** `packages/cli/src/cli/commands/start.ts` merges config and theme `filePaths`, deduplicates them, and watches each path with `watchConfigFiles(...)`. That is the existing truth seam for autoupdate. [VERIFIED: packages/cli/src/cli/commands/start.ts]
- **The most honest TSX-runtime test already exists:** `packages/cli/src/cli/commands/start.test.ts` runs `pnpm exec tsx --eval` against `packages/cli/src/render/dom-host.tsx` and asserts the rendered HTML succeeds without `React is not defined`. That is better proof than synthetic transform assumptions. [VERIFIED: packages/cli/src/cli/commands/start.test.ts]
- **The shared deck document is already centralized:** `packages/cli/src/render/dom-host.tsx` owns deck slots, theme CSS variables, stylesheet links, inline warnings, and outer shell styling for browser output. That is the right place to gate emulator-only chrome without creating a second renderer. [VERIFIED: packages/cli/src/render/dom-host.tsx]
- **Current tests already cover most neighboring seams:** `packages/cli/src/config/theme.test.ts` covers built-in theme file graphs and theme runtime reload; `packages/cli/src/render/dom-host.test.tsx` covers button frames and document output; `packages/cli/src/cli/commands/start.test.ts` covers watcher behavior and the real TSX runtime path. Phase 27 should extend these proof points rather than inventing new scaffolding first. [VERIFIED: packages/cli/src/config/theme.test.ts] [VERIFIED: packages/cli/src/render/dom-host.test.tsx] [VERIFIED: packages/cli/src/cli/commands/start.test.ts]

## Recommended Approach

Plan Phase 27 as two vertical slices, not four isolated cleanup chores. First, tighten the theme contract end-to-end: remove `legacy_yaml`, move fallback frame ownership onto the built-in default theme package, and prove the returned theme file graph still includes `themes/default/ButtonFrame.tsx` so the existing reload path remains truthful. [VERIFIED: packages/cli/src/config/theme.ts] [VERIFIED: packages/cli/src/config/theme.test.ts] [VERIFIED: packages/cli/src/cli/commands/start.ts]

Second, tighten the shared browser-renderer seam end-to-end: make the real TSX execution path succeed without manual React imports, add explicit emulator-mode gating for shell chrome inside `renderDomDeck(...)`, and prove both with the already-honest `start.test.ts` runtime assertion plus document-level assertions in `dom-host.test.tsx`. This keeps one renderer, one watch graph, and one runtime policy instead of layering compatibility hacks on top of shipped behavior. [VERIFIED: packages/cli/src/render/dom-host.tsx] [VERIFIED: packages/cli/src/render/dom-host.test.tsx] [VERIFIED: packages/cli/src/cli/commands/start.test.ts]
