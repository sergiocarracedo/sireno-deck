## Why this plan exists

Plan 75.1-04 split the deck Vite and emulator Vite into two separate roots (`packages/cli/frontend/` and `packages/cli/frontend-emulator/`) but only moved the *config files* (`index.html`, `vite.config.ts`, `vite-dev-entry.ts`). The actual React source files (`EmulatorShell.tsx`, `IframeCanvas.tsx`, `DeviceSelector.tsx`, `mouse-to-button.ts`, `devices.ts`, `main-emulator.tsx`) stayed in `packages/cli/frontend/src/`. This caused `GET /src/main-emulator.tsx → 404` on the emulator URL.

Independently, the user requested that the emulator page URL not carry the `?deck=...&ws=...&keyCount=...` query string — the emulator server should hand those URLs to the page internally instead.

## How the emulator mode flows now

1. User runs `pnpm cli:dev emulate --port 8912` (or `pnpm emulate --port 8912`).
2. CLI spawns WS bridge (port 52937) + Deck Frontend Server (auto-port) + Emulator Frontend Server (port 8912).
3. Emulator Vite reads `SIRENO_DECK_URL` + `SIRENO_WS_URL` + `SIRENO_KEY_COUNT` from env.
4. Emulator Vite serves `index.html` with `<script>window.__SIRENO__ = {deckUrl, wsUrl, keyCount};</script>` injected into `<head>`.
5. Page URL stays clean: `http://127.0.0.1:8912/`.
6. `EmulatorShell` reads `window.__SIRENO__` and opens a WS client + renders an `<iframe>` whose `src` is `deckUrl + ?ws=wsUrl + &mode=emulate&device=...` (the iframe URL still has `?ws=` because the DECK page reads it from `App.tsx:readWsUrlFromLocation()`).
7. User clicks over the iframe → mouse-to-button translator sends `button-action` over the emulator's own WS connection → CLI logs it.

## Architectural decision: env injection vs WS handshake

Two options were considered for getting URLs into the emulator page without a query string:

1. **Env → transformIndexHtml plugin** (chosen). Pros: works at SSR / Vite dev time, no JS roundtrip, visible in `view-source`, zero runtime coupling. Cons: requires the env vars to be set in the Vite child process (already works — `vite-server.ts:75` merges `opts.env` into child env).
2. **WS bridge "hello" message**. Pros: dynamic. Cons: needs a JS handshake before `EmulatorShell` can render anything; adds a third message type to the protocol; doesn't help if WS is unreachable.

Option 1 wins because (a) the URLs are stable for the lifetime of the process (they're the CLI's own ports), (b) the Vite child already inherits env from the CLI, and (c) the page can render synchronously without waiting for a WS roundtrip.
