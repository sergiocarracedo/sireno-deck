# v1.5 Requirements — Addons & UX Polish II

**Shipped:** 2026-06-10
**Total requirements:** 25
**Phases:** 7 (50-56)

## Weather — location by city name and geocoding (extends WX-*)

| ID | Requirement | Phase |
|----|-------------|-------|
| WX-07 | The weather addon's `location` config accepts either a string (e.g. `"Vigo, Spain"`) or the existing `{name, latitude, longitude}` object; the existing structure is preserved unchanged | 50 |
| WX-08 | When `location` is a string, the addon resolves it via the Open-Meteo Geocoding API (`geocoding-api.open-meteo.com/v1/search`) and uses the first returned match as the coordinates | 50 |
| WX-09 | Geocoding results are cached in-memory with a normalized lowercase key and a bounded LRU of at least 1000 entries to avoid repeated network calls when the same city is referenced | 50 |
| WX-10 | If geocoding returns no results or the network call fails, the addon shows an honest "location not found" state and does not silently fall back to IP geolocation | 50 |

## Weather — 2-day daily forecast (new WX2-*)

| ID | Requirement | Phase |
|----|-------------|-------|
| WX2-01 | The weather button adds a new `daily-forecast` page to its page cycle so users can reach a multi-day view by tapping past the hourly pages | 50 |
| WX2-02 | The `daily-forecast` page calls the Open-Meteo `/v1/forecast` endpoint with `daily=temperature_2m_max,temperature_2m_min,weather_code,precipitation_sum&forecast_days=2&timezone=auto`; the `timezone=auto` parameter is required so the 24h windows align to local day boundaries | 50 |
| WX2-03 | The `daily-forecast` page renders a row per day with: day-of-week label, weather code icon (reusing the existing WMO mapping), high temperature, low temperature, and precipitation sum | 50 |

## Bars content polish (new BARS-*)

| ID | Requirement | Phase |
|----|-------------|-------|
| BARS-01 | When a `Bars` item has no `color`, its label uses the active theme's primary color instead of the inherited text color | 51 |
| BARS-02 | Each bar renders its `value` inside the bar, rotated 90 degrees, in a color that is the visual negative of the bar pixels under the text (precomputed from `item.color` or a per-bar palette when the bar color is a known solid) | 51 |
| BARS-03 | When the bar's effective color is near gray (computed luma within 32 of 128) the value text falls back to white on dark bars and black on light bars, so it never becomes unreadable | 51 |

## Settings deck (new SETTINGS-*)

| ID | Requirement | Phase |
|----|-------------|-------|
| SETTINGS-01 | A new first-party `settings` addon is shipped under `packages/cli/src/builtin-addons/settings/` and provides a settings deck with brightness controls | 54 |
| SETTINGS-02 | The settings deck exposes a brightness-up button and a brightness-down button that adjust the device brightness in 10% steps using `@elgato-stream-deck/node` `setBrightness(0-100)` and apply the change to every open device | 54 |
| SETTINGS-03 | The main deck's reserved-slot button is replaced by a settings button that navigates to the settings deck; this is a deliberate breaking change to the v1.4 main-deck home button and is called out in CHANGELOG | 54 |
| SETTINGS-04 | The settings deck shows the project logo and the CLI version, replacing the main-deck home button that performed that role under v1.4 (the v1.4 home button is removed from the main deck reserved slot) | 54 |

## Lock deck access (new LOCK-*)

| ID | Requirement | Phase |
|----|-------------|-------|
| LOCK-01 | Users can navigate to the configured lock deck from the main deck even when the session is not locked, so the lock deck can be pre-warmed and inspected before locking the computer | 52 |
| LOCK-02 | When the session state is `locked`, the core does not inject the system-reserved back button into the lock deck, so the lock deck renders exactly as the user configured it without any system back affordance | 52 |

## Brightness device control (new BR-*)

| ID | Requirement | Phase |
|----|-------------|-------|
| BR-01 | The `StreamDeckDeviceHandle` exposes a `setBrightness(percentage: number)` method that maps `0..100` to the underlying `@elgato-stream-deck/node` `setBrightness` call for the device's product identifier and persists the value for reconnect | 53 |
| BR-02 | The brightness change applies to every currently open device handle in a single best-effort pass; failures on individual devices are logged but do not abort the pass | 53 |

## Active-app addon decks (new ACTIVEAPP-*)

| ID | Requirement | Phase |
|----|-------------|-------|
| ACTIVEAPP-01 | `AddonGeneratedDeck` accepts an optional `process_names: string[]` field; when the active foreground process matches any name in the list (case-insensitive substring match, also matching the OS-specific executable suffix), the deck is registered as an active-app deck | 55 |
| ACTIVEAPP-02 | When an active-app deck's process is the foreground app, that deck is shown overlaid on top of the current base deck; the overlay deck uses its own local page history but does not push entries onto the base deck's navigation stack | 55 |
| ACTIVEAPP-03 | In an active-app overlay deck, the reserved-slot button is a toggle button (icon + label "Base" or similar) that dismisses the overlay and returns to the base deck, replacing the system back button for that deck | 55 |
| ACTIVEAPP-04 | When the user is on a base deck and an active-app deck is currently overlaid, double-tapping the system back button dismisses the overlay (returning to the base deck) instead of performing the normal back action | 55 |
| ACTIVEAPP-05 | Active-app overlay decks support internal pagination like any other deck; pages advance with the same n-2 / reserved-slot conventions as the emoji selector and the toggle button remains on every page | 55 |
| ACTIVEAPP-06 | The active-app foreground process is detected via the `active-win` package on all three supported OSes; the addon API version is **not** bumped (changes are additive and backwards compatible) | 55 |
