# Plan 20-01: Theme Package Resolution and Theme-Owned Frame Contract

<objective>
Land the first tracer bullet for Phase 20 by making themes real manifest-backed packages on the shipped browser path. This slice converts theme resolution from YAML-only lookup into a package-or-path contract, then proves the new runtime seam end-to-end by rendering non-full-surface buttons through a mandatory theme-owned `buttonFrame` that receives only `idle | tap | hold` visual state while core keeps slot sizing and host layout ownership.
</objective>

## Tasks

<task id="20-01-01">
<title>Replace YAML-only theme lookup with manifest-backed package resolution</title>
<files>
- packages/cli/src/config/theme.ts
- packages/cli/src/config/theme.test.ts
- packages/cli/src/cli/commands/start.ts
- themes/default/manifest.yml
- themes/default/index.tsx
- themes/light/manifest.yml
- themes/light/index.tsx
</files>
<action>
Refactor the theme loader so `resolveTheme(...)` accepts the existing overloaded config string but resolves it through explicit builtin theme id, filesystem path, and package-root attempts, with one path-aware diagnostic when all attempts fail. Mirror the addon loader pattern instead of inventing a second packaging model: require a manifest-backed theme root with a mandatory JS runtime entry, load the runtime entry dynamically, and keep the resolved theme tokens plus runtime exports together as one theme object consumed by startup. Convert the built-in shipped themes onto that package contract so `dark` and `light` continue working as stable builtin ids during the migration.
</action>
<verify>
Run `pnpm --filter sireno-deck-cli exec vitest run src/config/theme.test.ts` and confirm the suite covers builtin package lookup, local-path package lookup, and explicit missing-theme diagnostics.
</verify>
<done>
The config/startup path resolves manifest-backed built-in and local themes through one loader seam, and the old YAML-only contract is no longer the only working path.
</done>
</task>
