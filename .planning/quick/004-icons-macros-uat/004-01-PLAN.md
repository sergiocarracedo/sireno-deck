# Plan 004-01: UAT icon/macro bugs — fixes for chrome-overlay, vscode-overlay, and core:action

<objective>
Three real-hardware bugs reported during Phase 10 UAT:
1. **type:// macros don't fire on core:action buttons** — `core:action` is missing `gestureHandlers: ['tap']` in the core addon manifest, so the addon registry strips the `tap` gesture handler at startup (default-deny policy).
2. **External addon deck icons don't resolve** — `addon://vscode-overlay/...` and `addon://chrome-overlay/...` fail because `addonDirs` is built only from builtin addons. Need to merge in addon dirs from the config's `addons:` list (the external addons are registered via `sirenodeck.json` manifests).
3. **chrome-overlay button labels don't show** — `deriveLabel` for `core:action` only checks `config.command`. Chrome-overlay buttons use `config.label` (e.g. "New Tab") with no `config.command`. Need to fall back to `config.label`.

Each fix is small and isolated. This plan ships all three as one vertical slice because they all share the user-facing symptom "addon overlay buttons don't work / don't render correctly".
</objective>

<files>

<action>
Edit `packages/cli/src/builtin-addons/core/index.ts`:

Find `'core:action': {` in the `buttonTypes` block. Currently:
```ts
'core:action': {
  frontend: actionFrontend,
  service: actionBackend,
},
```

Change to:
```ts
'core:action': {
  frontend: actionFrontend,
  service: { ...actionBackend, gestureHandlers: ['tap'] as const },
},
```

This mirrors how `core:change-deck`, `core:toggle`, and `core:page-nav` declare `gestureHandlers: ['tap']` (or `['tap', 'hold']`). Without this, the addon registry's default-deny policy (`packages/cli/src/addon/registry.ts:44-56`) strips the `tap` gesture from `core:action` buttons, which silently breaks `type://` macros and any addon-deck button that uses `actions.tap`.

Note the README already says "Command goes in `actions.tap`" (line 21 of `packages/cli/src/builtin-addons/core/README.md`) — so the intent was always for `tap` to be a valid gesture on `core:action`. The current code is the bug.

<action>
In `packages/cli/src/cli/commands/run.ts`, find where `resolverOptions` is built (around line 821: `buildResolverOptions(addonBundle.addonByType, [...])`). The addonDirs map is built from `addonBundle.addonByType` which only contains builtins.

The external addons (`vscode-overlay`, `opencode-overlay`, `chrome-overlay`) are loaded separately when the config is loaded — their `sirenodeck.json` manifests are read and their entries are imported. The config loader knows about these addons.

The fix: after loading the config (around line 412 `loaded = await loadConfig`), extract the external addon entries (from `loaded.config.addons`) and pass them to `buildResolverOptions` as additional addonDirs.

The `addons:` config field is an array of strings — paths to external addon directories. For each path, the entry file is `index.js` (per the JSON manifest).

Specifically:
1. Resolve each `loaded.config.addons` path against `loaded.configPath`'s directory (use `expandHome` or `resolvePath(dirname(configPath), addon)`).
2. For each resolved path, the addon dir is the directory itself. The addon name is the basename (e.g. `chrome-overlay` for `~/works/opensource/sireno-deck-addons/chrome-overlay`).
3. Add these to a Map: `addonName -> absoluteAddonPath`.
4. Pass this map to `buildResolverOptions` along with the existing addonByType map.

Implementation sketch:
```ts
const externalAddonDirs = new Map<string, string>()
for (const addonSpec of loaded.config.addons ?? []) {
  const addonPath = resolvePath(dirname(loaded.configPath), expandHome(addonSpec))
  const addonName = basename(addonPath)
  externalAddonDirs.set(addonName, addonPath)
}

const resolverOptions = buildResolverOptions(
  addonBundle.addonByType,
  [...],
  externalAddonDirs,  // ← merge with builtins
)
```

Update `buildResolverOptions` signature in `packages/cli/src/deck/deck-config.ts` to accept an optional `extraAddonDirs` parameter:
```ts
export const buildResolverOptions = (
  addonByType: ReadonlyMap<string, AddonFrontendRef>,
  baseDirs: ReadonlyArray<string>,
  extraAddonDirs?: ReadonlyMap<string, string>,
): ResolveIconPathOptions => {
  const addonDirs = new Map<string, string>()
  for (const ref of addonByType.values()) {
    if (ref.frontendEntry !== null) {
      addonDirs.set(ref.name, dirname(ref.frontendEntry))
    }
  }
  // ponytail: external addons (loaded from config's addons: list) need their dirs
  // registered too so `addon://<name>/assets/icon.png` resolves. The basenames
  // match the addon names in the deck triggers.
  for (const [name, dir] of extraAddonDirs ?? []) {
    addonDirs.set(name, dir)
  }
  return { addonDirs, baseDirs }
}
```

If `expandHome` doesn't exist as a util, use a simple inline replacement: `path.replace(/^~/, os.homedir())`.
