# Phase 61 — Icon updates

> Two independent icon swaps in the system-button layer. The two parts share a
> single plan because they together deliver one v1.6 design-language update and
> are both contained in `packages/cli/src/deck/system-buttons/`.

## Source decisions

- CONTEXT.md → data source: pass `overlayDeckId` + the resolved active deck
  config to the overlay toggle's render closure (no new hook API).
- CONTEXT.md → dual-icon layout: `send-to-back` background + deck-icon badge
  foreground + deck-name label.
- RESEARCH.md → use `<Icon>` (not a custom SVG), keep
  `MainLabelSurface` for the system back swap, use a small dedicated render
  function for the overlay toggle's dual-icon layout (YAGNI — no shared
  `DualBadge` component).

## Tasks

### Task 1: Swap system back default icon to `undo2`

**File:** `packages/cli/src/deck/system-buttons/SystemBackButton.tsx` (line 16)

**Requirement:** ICON-01

Change the default icon name from `chevron-left` to `undo2`:

```diff
-         main={{
-           name: backIconOverride ?? 'chevron-left',
-         }}
+         main={{
+           name: backIconOverride ?? 'undo2',
+         }}
```

**Why:** `undo2` is the v1.6 design-token for the "go back" gesture — a curved
arrow that reads as "undo this navigation step" rather than the spatial
"previous direction" reading of `chevron-left`. The `backIconOverride` prop is
preserved so per-deck overrides still work.

**Verify:** `pnpm --filter sireno-deck-cli test` — the existing
`__tests__/system-buttons-dispatcher.test.ts` does not assert on icon names;
the change is purely visual. No new unit tests needed for this one-line swap
(visual verification on real hardware is the contract — see
`61-VERIFICATION.md`).

**Done:** `SystemBackButton.tsx:16` default is `'undo2'`; the
`backIconOverride ?? 'undo2'` shape is unchanged.

### Task 2: Make `OverlayToggleButton` accept an active-overlay prop

**File:** `packages/cli/src/deck/system-buttons/OverlayToggleButton.tsx`

**Requirement:** ACTIVEAPP-08

Rewrite the component to accept a single prop, `activeOverlayDeck`, of type
`DeckConfig | null`. Render layout:

- **Background layer:** `<Icon name="send-to-back" size={48} tone="muted" />` —
  the larger, muted send-to-back glyph.
- **Foreground badge** (bottom-right of the background, absolute positioned):
  - If the deck name starts with an emoji char, render it via
    `<span className="text-base leading-none">{emoji}</span>` (or use the
    existing `isIconSource` helper from `MainLabelSurface.tsx:7-21` to
    distinguish emoji from text).
  - Otherwise, render a small `<Icon name="layout-grid" size={18} tone="accent" />`
    as a generic "deck" affordance.
- **Label:** the deck's `name` if present, else the deck `id`. When
  `activeOverlayDeck` is null, the label is `"Show App"` and the badge is
  hidden (only the background `send-to-back` icon shows).

Wrap the whole thing in a `<ButtonSurface data-sireno-overlay-toggle="true">`
(preserves the existing DOM hook).

Use a small inline render — NOT `MainLabelSurface` (per CONTEXT: "a small
dedicated render function (not a generic component) since the layout is
specific to this one button").

**Why:** The current `OverlayToggleButton` is a stateless component with no
awareness of which overlay is active. The CONTEXT decided the cleanest path is
to keep it stateless and have the runtime's render closure pass the resolved
active deck as a prop — matches the existing `system-back` precedent
(runtime.ts:1057-1066) which also reads derived state from the closure.

**Verify:** See Task 4 for the new component test.

**Done:** `OverlayToggleButton` exports a single component that takes
`activeOverlayDeck: DeckConfig | null` and renders the dual-icon layout.

**Verify:** `pnpm --filter sireno-deck-cli test` — the existing

**Done:** `runtime.ts:1033` passes `activeOverlayDeck` derived from the

### Task 4: Add unit tests for `OverlayToggleButton`

**File:** `packages/cli/src/deck/system-buttons/__tests__/OverlayToggleButton.test.tsx` (new)

Create the test directory and file. Test cases:

1. **renders neutral state when `activeOverlayDeck` is null** — the
   `send-to-back` icon is present, the badge is absent, the label is
   `"Show App"`.
2. **uses the deck's `name` as the label** — pass
   `activeOverlayDeck={{ id: 'chrome', name: 'Chrome', buttons: [] }}`,
   assert the label is `"Chrome"`.
3. **falls back to deck `id` when `name` is missing** — pass
   `activeOverlayDeck={{ id: 'chrome', buttons: [] }}`, assert the label is
   `"chrome"`.
4. **extracts emoji char from the deck name as the badge** — pass
   `activeOverlayDeck={{ id: 'netflix', name: '📺 Netflix', buttons: [] }}`,
   assert the badge contains the emoji and the label is `"📺 Netflix"`.
5. **falls back to `layout-grid` icon when the name has no emoji** — pass
   `activeOverlayDeck={{ id: 'chrome', name: 'Chrome', buttons: [] }}`, assert
   the badge is the `layout-grid` icon (use the `data-sireno-icon` test
   attribute if `<Icon>` exposes one; otherwise assert on the badge
   container's child count or a `data-testid` you add).

For DOM assertions, use the project's existing `renderReactNodeToHtml`
helper from `@/render/dom-host` (see `BrightnessSurface.test.tsx` for the
canonical pattern):

```ts
import { createElement } from 'react'
import { describe, expect, it } from 'vitest'
import { renderReactNodeToHtml } from '@/render/dom-host'
import { OverlayToggleButton } from '../OverlayToggleButton'

function render(activeOverlayDeck: Parameters<typeof OverlayToggleButton>[0]['activeOverlayDeck']) {
  return renderReactNodeToHtml(
    createElement(OverlayToggleButton, { activeOverlayDeck }),
  )
}

describe('OverlayToggleButton', () => {
  it('renders the neutral state with "Show App" label when no overlay is active', () => {
    const html = render(null)
    expect(html).toContain('send-to-back')
    expect(html).toContain('Show App')
  })

  it('uses the deck name as the label when one is present', () => {
    const html = render({ id: 'chrome', name: 'Chrome', buttons: [] })
    expect(html).toContain('Chrome')
  })

  it('falls back to deck id when name is missing', () => {
    const html = render({ id: 'chrome', buttons: [] })
    expect(html).toContain('chrome')
  })

  it('extracts the leading emoji char from the deck name as the badge', () => {
    const html = render({ id: 'netflix', name: '📺 Netflix', buttons: [] })
    expect(html).toContain('📺')
  })

  it('falls back to the layout-grid icon when the name has no emoji', () => {
    const html = render({ id: 'chrome', name: 'Chrome', buttons: [] })
    expect(html).toContain('layout-grid')
  })
})
```

Add `data-testid` or `data-sireno-overlay-badge` attribute on the badge
container if needed for the "no badge in neutral state" assertion. Use the
existing `data-sireno-overlay-toggle="true"` (already on the outer
`ButtonSurface`) as the test anchor.

**Why:** The dual-icon layout has more state than the old single-icon layout.
A 5-test suite locks in the neutral state, label precedence, and the
emoji-extraction heuristic so future refactors don't silently regress the
visual.

**Verify:** `pnpm --filter sireno-deck-cli test src/deck/system-buttons`.

**Done:** 5 unit tests for `OverlayToggleButton` cover all branches of
`activeOverlayDeck` (null, name only, id-only, emoji name, no-emoji name).

## Deviations / Open Questions

- **Emoji extraction:** we use the same `isIconSource` predicate from
  `MainLabelSurface.tsx:7-21`. If the predicate gets a refactor, the
  badge logic follows it. Alternative: inline a simpler
  `^\p{Extended_Pictographic}` regex check. The existing helper is
  preferred for consistency.
- **Deck icon field:** `DeckConfig` has no `icon` field. The badge always
  derives from the deck's name (emoji char) or a generic icon. If the
  Chrome overlay deck (Phase 64) needs a more specific icon, that's a
  Phase 64 follow-up — adding `icon?: string` to `DeckConfig` is one line
  if needed.
