# Plan 25-02: Harden Custom Theme TSX Loading And Boundaries

<objective>
Make the widened theme contract honest for users, not just for the built-in proof theme: a custom manifest-backed theme can author `manifest.main` in `.tsx` with sibling relative imports inside the package root, and the resolver explicitly rejects imports that escape that root.
</objective>

## Tasks

<task id="25-02-01">
<title>Enforce the in-root relative-import boundary for theme runtime graphs</title>
<files>
- packages/cli/src/config/theme.ts
</files>
<action>
Extend `packages/cli/src/config/theme.ts` so the same resolver that already walks theme runtime relative imports also enforces the Phase 25 boundary: relative imports are supported only when they stay inside the theme package root. Mirror the repo's raw-addon honesty rather than inventing broader behavior: keep `manifest.main` as the only entrypoint, allow normal in-root sibling imports for `.js/.jsx/.ts/.tsx`, and fail with a path-aware theme validation/import error when the runtime graph escapes the theme root.
</action>
<verify>
`grep -n "isWithinRoot\|theme package root\|relative import" packages/cli/src/config/theme.ts` shows the explicit theme-root boundary enforcement alongside the existing runtime graph traversal.
</verify>
<done>
The theme loader has one explicit import-boundary rule that matches Phase 25 context and no longer accidentally implies workspace-wide TypeScript loading.
</done>
</task>

<must_haves>
- This slice must keep the built-in/custom theme contract unified; do not add a custom-theme-only loader seam.
- The supported contract stays self-contained and portable: relative imports inside the theme root are allowed, imports outside it are not.
- Error coverage must prove the boundary explicitly instead of relying on incidental Node import failures.
</must_haves>
