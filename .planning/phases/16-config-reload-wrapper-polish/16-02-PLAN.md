# Plan 16-02: Live Reload Valid Config And Preserve User Navigation

<objective>
Add the happy-path reload tracer bullet: when someone edits `config.yml` or a referenced deck file, the running daemon reloads into the new valid config and keeps the user's place when the new config still supports it. A completed plan should prove live continuity on the real runtime path, not just static loader correctness.
</objective>

## Tasks

<task id="16-02-01">
<title>Track loaded config files and watch the active config graph</title>
<files>
- packages/cli/src/config/loader.ts
- packages/cli/src/cli/commands/start.ts
</files>
<action>
Extend the runtime-config loading path so startup can know which files participated in the last successful config load: the root config plus any referenced deck files. Use that information to introduce a narrow reload manager in the daemon startup path that watches exactly those active files, refreshes the watch set after each successful reload, and debounces editor-style multi-event writes enough to avoid duplicate reload storms.
</action>
<verify>
Run `grep -n "watch\|reload\|filePath" packages/cli/src/cli/commands/start.ts && grep -n "file" packages/cli/src/config/loader.ts`.
</verify>
<done>
The startup path knows the active config graph and can react to changes in the real files users edit.
</done>
</task>

<task id="16-02-02">
<title>Rebuild runtime on successful reload and restore the best valid navigation state</title>
<files>
- packages/cli/src/cli/commands/start.ts
- packages/cli/src/deck/runtime.ts
- packages/cli/src/deck/runtime.test.ts
</files>
<action>
Implement the successful reload flow end-to-end: capture the current runtime navigation stack, load the new config snapshot, dispose the old runtime cleanly, construct a new runtime from the new config, and restore user state using the agreed rule set. Preserve the full stack when every deck on it still exists, otherwise preserve the active deck alone if it still exists, otherwise fall back to `main_deck`. Treat reload as authoritative by recreating runtime instances from scratch instead of trying to migrate internal toggle or scheduler state across configurations.
</action>
<verify>
Run `pnpm --filter sireno-deck-cli test -- src/deck/runtime.test.ts`.
</verify>
<done>
Successful live reload is observable, preserves the strongest valid user context, and avoids state-migration heuristics.
</done>
</task>

<must_haves>
- Reloaded configs can come from either root-file edits or referenced deck-file edits.
- Successful reload continuity reuses the repo's existing full-stack restore philosophy instead of resetting users to the main deck unnecessarily.
- The runtime is rebuilt cleanly on success; old instance state does not leak across reloads.
</must_haves>
