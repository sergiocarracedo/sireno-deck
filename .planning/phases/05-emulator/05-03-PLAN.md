# Phase 05 Plan 03 — Mouse-to-Gesture + WS Action Injection (tracer bullet)

## Context

Plan 02 ships the shell + iframe + side panel placeholders. Plan 03 wires it all together:

1. **Mouse-to-gesture mapping** in `DeckFrame`: the iframe can't see the host's mouse events (different origin), so we render an overlay grid over the iframe. Each grid cell captures mouse events (down/move/up) and feeds them through the gesture state machine (from `packages/cli/src/core/gesture-state.ts`) to produce `tap | dbl-tap | hold`.

2. **WS client** in `bridge.ts`: connects to the CLI's WS bridge (port 52937), sends `hello` with the SIRENO_TOKEN, then on each gesture publishes a `button-action` message. Subscribes to `decks-list`, `deck-config`, `state`, `show-overlay` for the action log + state inspector.

3. **Action log integration**: each WS message gets appended to the action log (in SidePanel).

This is the user-observable tracer bullet for Phase 05: a click in the emulator produces a `button-action` and the shell's action log updates.

## Notes for executor

- The mouse event coordinates relative to the cell determine which cell was hit. Use `event.currentTarget` as the cell ref.
- The gesture state machine from `@sireno-deck-2/cli` is a pure function — call it with `{ type: 'down' | 'up', timestamp: number }[]`.
- The iframe overlay uses `pointer-events: auto` on cells, `pointer-events: none` on the iframe. The cells must be `transparent` so the user sees the deck underneath.
- For the integration test, mock `@sireno-deck-2/cli/bridge` (or pass a fake `createEmulatorWsClient` via dependency injection). Pattern: add a `wsClient` prop to App.
