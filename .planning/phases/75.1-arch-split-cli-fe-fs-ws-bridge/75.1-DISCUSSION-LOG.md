## Gray Areas Discussed

### 1. Frontend Server process model

**Question:** How should the Vite Frontend Server be hosted relative to the CLI process?

| Option | Verdict |
|--------|---------|
| **Spawned child process (Recommended)** | ✅ Accepted |
| In-process Vite programmatic API (`createServer` in same Node process) | Considered |
| External `vite` CLI binary (shelled out, sibling process) | Considered |

**User choice:** Spawned child process.

**Rationale (user implicit, recommendation rationale explicit):**
- Matches the architecture diagram's "Frontend Server" as a peer box.
- Clean crash boundary: Vite runtime errors don't kill the CLI; CLI can restart the child on non-fatal exits.
- Vite version is pinned by the CLI's package.json, so the "external binary" decoupling isn't actually useful here.
- The "in-process" option would couple Vite's startup lifecycle to the CLI process, which complicates HMR (Vite's dev server assumes it owns the Node event loop for HMR file watching).

---

### 2. WebSocket bridge ownership & address binding

**Question:** Who owns the WS bridge server, and on what address does it bind?

| Option | Verdict |
|--------|---------|
| **CLI owns it on `localhost:WS_PORT` (Recommended)** | ✅ Accepted |
| Frontend Server owns it (Vite middleware attaches `ws.Server` via `configureServer`) | Considered |
| CLI owns it, Frontend Server proxies | Considered |

**User choice:** CLI owns it on `localhost:WS_PORT`.

**Rationale:**
- Matches the diagram (WS bridge box is inside the CLI box).
- Hardware button presses → CLI's WS bridge → frontend runner is the cleanest directionality. If the Frontend Server owned the bridge, CLI would have to be a WS client to its own served app, which inverts the data flow.
- Separate port from Vite's HTTP port avoids interference with Vite's middleware pipeline.
- Localhost-only binding (no auth token) is acceptable because the CLI is single-user; threat model excludes remote callers.

---

### 3. Headless browser lifecycle (real mode)

**Question:** When should the headless Chromium browser be (re)spawned in real mode?

| Option | Verdict |
|--------|---------|
| **Per-session (Recommended)** | ✅ Accepted |
| Per-deck (respawn on every active-deck change) | Considered |
| Per-active-deck with reset (reset only on regular/overlay boundary) | Considered |

**User choice:** Per-session.

**Rationale:**
- Respawning headless Chromium costs ~500ms per navigation. With the React router doing deck navigation, there's no render-state leakage that requires respawn.
- SPA routing preserves React state across deck changes (e.g., an emoji-selector's in-flight search term doesn't reset when you navigate away and back).
- The "reset on regular/overlay boundary" option is a compromise that adds complexity for a benefit that's only theoretical — overlay decks use a different React tree, so state leakage is impossible by construction.

---

### 4. dom-host/ retirement

**Question:** What happens to the existing in-process React reconciler at `packages/cli/src/render/dom-host/`?

| Option | Verdict |
|--------|---------|
| **Retire entirely (Recommended)** | ✅ Accepted |
| Keep as startup placeholder fallback (CLI paints first frame via `renderDomDeck` until Chromium connects) | Considered |
| Keep for base-deck rendering only (overlay decks render in browser app) | Considered |

**User choice:** Retire entirely.

**Rationale:**
- Single render path is much simpler to reason about — one source of truth for "what the user sees."
- The startup-placeholder use case is solvable with a CLI-side startup image (`assets/logoFull.png`) that hands off on first snapshot, which is what Phase 38 already implemented.
- Base-deck-only rendering optimization is overkill for a Stream Deck (15 keys, 5fps max) — there's no Chromium bottleneck at this scale.

## Decisions Locked

1. Frontend Server = spawned child process (Vite supervised by CLI)
2. WS bridge = CLI-owned on `localhost:WS_PORT`, separate from Vite's HTTP port
3. Headless Chromium = per-session (one browser for the whole CLI session)
4. `dom-host/` = retired entirely, no fallback
