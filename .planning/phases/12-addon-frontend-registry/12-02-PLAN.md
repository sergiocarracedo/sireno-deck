# Phase 12 Plan 02: CLI state publishing (lazy, namespaced)

## Tasks

### Task 1: Invert the WS state flow

- File: `packages/cli/src/render/ws-bridge.ts`
- The bridge already has `broadcast(message)`. Add a `broadcastState(channels: Record<string, unknown>)` helper that wraps it: `{type: "state", channels}`.
- Add a `statePublishIntervalMs` constant (default 1000ms; CLI sends heartbeat state to keep WS alive + confirm cadence).

### Task 2: State publisher

- File: `packages/cli/src/render/state-publisher.ts` (new)
- `StatePublisher` class:
  - Constructor: takes a `WsBridge`, an `AddonRegistry`, and a logger.
  - `start()` — begins the publisher's polling loop.
  - `stop()` — clears all intervals.
  - `setActiveDeck(deck)` — diffs the new deck's buttons against the previous, starts/stops polling for added/removed addon types.
  - `publishChannel(channel: string, payload: unknown)` — broadcasts via `bridge.broadcastState({ [channel]: payload })`.
- Polling cadence: each addon declares `publishIntervalMs` in its manifest (Plan 12-01 added this). The publisher uses `setInterval` per channel.

### Task 3: Wire state publisher into the runtime

- File: `packages/cli/src/cli/commands/run.ts`
- In `runEmulatorLifecycle`, instantiate `StatePublisher` and subscribe to the runtime's `deck-active` channel.
- On `deck-active`, call `statePublisher.setActiveDeck(deck)`.
- On shutdown, call `statePublisher.stop()`.

### Task 4: Channel namespace convention

- Channel names: `<addon-name>:<key>`. E.g., `date-time:now`, `weather:current`.
- The publisher is given a map `addonName → (key: string, poll: () => Promise<unknown>)`. For each addon currently in the active deck, the publisher sets up an interval that calls `poll()` and publishes to `<addon-name>:<key>`.
- The default cadence: `date-time:now` = 1000ms, `weather:current` = 600000ms, `system-status:metrics` = 1000ms, `media-player:state` = 2000ms, `brightness:current` = 2000ms, `value-display:values` = 5000ms.

### Task 5: State message schema (per-channel cadence)

- File: `packages/cli/src/api/protocol-internal.ts`
- The existing `stateMessageSchema` is `{type: "state", channels: Record<string, unknown>}`. Add a `cadence?: Record<string, number>` field that tells the frontend when to expect updates per channel. The CLI publishes this in `hello-ack` and the periodic heartbeat.

### Task 6: Tests + typecheck + lint

- New tests for `StatePublisher`:
  - Lazy poll lifecycle: starts when addon appears, stops when it disappears.
  - Channel publishing: payloads land on the WS bridge.
  - `publishIntervalMs` from manifest is honored.
- All existing 464 tests pass.
- `pnpm --filter sireno-deck typecheck` clean.
- `pnpm --filter sireno-deck lint` clean.

## Acceptance

- CLI publishes state via WS state messages.
- Each addon channel uses its own cadence from `publishIntervalMs`.
- Polls are started/stopped based on the active deck's button set (lazy).
- The frontend `ChannelRegistry` receives the publishes (existing `bridge/client.ts` already routes `state` messages to `ChannelRegistry`).
