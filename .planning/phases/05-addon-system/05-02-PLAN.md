# Plan 05-02: Load real addons from local folders and npm

<objective>
Deliver the external-addon installation slice for Phase 5. This plan turns the registry from a bundled-only proof into the real extension loading path with manifest validation, apiVersion checks, and startup behavior that isolates broken addons instead of taking down the CLI.
</objective>

## Tasks

<task id="05-02-01">
<title>Add manifest schema and unified addon loader for local and npm sources</title>
<files>
- packages/cli/src/addon/manifest.ts
- packages/cli/src/addon/manifest.test.ts
- packages/cli/src/addon/loader.ts
- packages/cli/src/addon/loader.test.ts
- packages/cli/src/addon/registry.ts
</files>
<action>
Create `packages/cli/src/addon/manifest.ts` with the core-owned manifest schema, including the required addon entrypoint information and the versioned `apiVersion` contract chosen in project state. Then add `packages/cli/src/addon/loader.ts` that can resolve addon entrypoints from local-folder config and npm package names through the same dynamic-import path, validate each manifest, and convert successful loads into registry registrations. Keep the loader contract explicit about one-addon-at-a-time failures so later startup code can log warnings and continue.
</action>
<verify>
grep 'apiVersion' packages/cli/src/addon/manifest.ts && grep 'import(' packages/cli/src/addon/loader.ts && grep 'source' packages/cli/src/addon/loader.ts
</verify>
<done>
The codebase has a unified manifest and addon loading layer that can describe both local and npm addon sources before startup wiring uses it.
</done>
</task>
