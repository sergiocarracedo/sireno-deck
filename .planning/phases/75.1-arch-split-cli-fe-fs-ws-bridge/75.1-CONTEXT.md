# Phase 75.1: Architecture split — CLI / Frontend Server / Frontend + WebSocket bridge — Context

**Gathered:** 2026-06-21
**Mode:** standard
**Status:** Ready for planning

<domain>
## Phase Boundary

Re-architect the runtime into three cleanly separated layers with a WebSocket bridge mediating between the CLI/Backend and the browser-based runner:

- **CLI / Backend** owns OS interaction, command execution, hardware lifecycle, global state, and the WebSocket bridge server.
- **Frontend Server** (Vite, child Node process) serves the React frontend, themes, addon components, and builtin addons with HMR. In emulation mode it also serves the deck placeholder + emulator control panels (device selector, virtual button emulation via mouse).
- **Frontend** (React app) renders decks and buttons, uses router navigation. Regular decks push history; overlay decks do not.
- **Real mode**: CLI spawns headless Chromium (Playwright), which connects to the Frontend Server, renders the active deck, and returns snapshots that the CLI pushes to the Stream Deck. Hardware button presses flow back through the WS bridge.
- **Emulation mode**: user opens the Frontend Server URL in their own browser; the React app loads inside an iframe; emulated button presses flow through the WS bridge exactly as hardware presses would.

This phase is a re-architectural foundation — no new product capabilities are introduced. Existing addon registry, system-status, date-time, brightness, value-display, weather, emoji-selector, media-player flows must remain functional.

</domain>

<decisions>
## Implementation Decisions

### Frontend Server lifecycle
- **Spawned child process** — CLI spawns Vite as a supervised child Node process via `child_process.spawn`. CLI supervises via stdout/stderr consumption and `exit` events; restarts the child on crash up to N times. Matches the architecture diagram's "Frontend Server" as a peer box. Clean crash boundary; Vite runtime upgrades are independent of CLI release.

### WebSocket bridge ownership & binding
- **CLI owns it on `localhost:WS_PORT`** — separate from Vite's HTTP port. CLI starts a `ws.Server` bound to `127.0.0.1:WS_PORT` (port auto-selected, surfaced via CLI logging). Headless Chromium and user browser both open WebSocket client connections to it. Frontend Server only serves HTTP. Matches the architecture diagram (the WS bridge box lives inside the CLI box).
- **No auth token required** — bridge binds to localhost only. Any process on the local machine can connect. Acceptable because the CLI is single-user; threat model excludes remote callers.

### Headless browser lifecycle (real mode)
- **Per-session** — CLI spawns headless Chromium once at startup and keeps it alive for the entire CLI session. Deck changes navigate via SPA routing (React router handles the new deck); the headless browser is not respawned. React state preserved across deck changes; minimal cold-start cost; snapshot diffing still applies on the rendered page.

### dom-host/ retirement
- **Retire entirely** — delete `packages/cli/src/render/dom-host/` and all `renderDomDeck` call sites. All rendering moves to the browser React app loaded by Vite. Single render path; one source of truth for what users see; simpler architecture. No fallback to in-process rendering.

### Agent's Discretion
The following decisions are deferred to the planner/executor (no user preference captured):

- Router library choice (React Router v6+, TanStack Router, hand-rolled) — pick what fits the React 19 + HMR stack.
- WS message schema versioning cadence — independent from `SIRENO_ADDON_API_VERSION` or shared; pick one and document.
- Addon frontend surface contract — how addon React components reach the Vite bundle (dynamic `import()` from addon manifest `frontend` entry vs static registration at startup). Must work for bundled addons AND raw-source addons.
- Snapshot diffing strategy (full vs delta) — current is full per Phase 35; the new in-browser render may make delta viable.
- Headless Chromium flags (sandbox, GPU, --disable-blink-features) — match current `BrowserLauncher` defaults.
- Frontend Server port (static vs auto-selected) — auto-select to avoid clashes in dev; document in README.
- CLI supervision policy for the Vite child (max restart attempts, backoff, what counts as a fatal crash) — pick sensible defaults.
- Emulator mode mouse-event handling — does the iframe include the mouse-emulation code, or does the outer user-browser page translate mouse coords into WS button-action messages?

</decisions>

<specifics>
## Specific Ideas

- **Frontend Server must provide HMR for addon code** — the user explicitly called this out. Vite's HMR is a hard requirement, not a nice-to-have.
- **Emulator panels render in the Frontend Server, not the iframe** — the architecture diagram shows the device selector and mouse-emulation code as a sibling of the deck iframe inside the user browser, served by the Frontend Server (not the CLI). The iframe is a pure canvas.
- **Router navigation, not full page reload** — regular decks push history; overlay decks replace without history. The user emphasized the history distinction.
- **WebSocket bridge is "must be implemented"** — the user flagged the WS bridge as not-yet-existing. This phase is where it gets built.
- **WS message schema** (from the user's description):
  - CLI → runner: `deck-config`, `state`, `button-config`
  - runner → CLI: `button-action` (real hardware or emulated), `snapshot` (real mode only), `method-call` (command execution, addon backend calls)

</specifics>

## Existing Code Insights

### Reusable Assets
- **`BrowserLauncher` / `BrowserLike` / `BrowserPageLike`** (`packages/cli/src/render/browser-renderer.ts`) — already transport-agnostic. The refactor keeps the abstraction; only the launch target changes (Vite URL → Playwright connection to that URL).
- **`chromium-detect.ts`** — Playwright Chromium auto-install. Reused; no changes needed.
- **Addon registry** (`packages/cli/src/addon/`) — stays in CLI; addon manifests still load via the existing path; only their `render()` method consumers change (from in-process reconciler to React app via WS bridge).
- **Built-in addons** (`packages/cli/src/builtin-addons/`) — their surface components already export React TSX; they will move from in-process rendering to browser rendering via the WS bridge without addon code changes.

### Established Patterns
- **Process supervision in CLI**: yargs command structure, daemon lifecycle (`startDaemon` / `stopDaemon`), pino logging. New Vite child process supervision follows the same pattern (stdout/stderr → pino, exit event → restart or fatal).
- **Snapshot pipeline**: current path is `renderDomDeck → sharp → write cache → device`. New path is `Chromium page → Playwright screenshot → sharp → write cache → device`. Sharp + write cache stays in CLI.
- **Config validation**: existing zod schemas in `packages/cli/src/core/schemas.ts`. No schema changes needed for this phase.
- **Theme/addon asset pipeline**: `addon://` and `theme://` URL rewriting exists today. Reused.

### Integration Points
- **`packages/cli/src/cli/commands/start.ts`** — main refactor target. Decompose into: WS bridge server, Frontend Server child process supervisor, headless Chromium launcher (real mode), user-browser connection handler (emulation mode), hardware event forwarder.
- **`packages/cli/src/render/dom-host/`** — delete entirely. Inventory files: `button.tsx`, `deck-document.tsx`, `key-slot.tsx`, `hosted-button-content.tsx`, `index.tsx`.
- **New `packages/cli/frontend/`** — Vite-served React app entry. Houses the router, deck/button components (moved from `dom-host/`), addon frontend loader, WS client.
- **New `packages/cli/src/render/ws-bridge.ts`** — WS server + message router. CLI side.
- **New `packages/cli/src/render/frontend-server.ts`** — Vite child process supervisor. CLI side.
- **New `packages/cli/src/render/browser-runner.ts`** — wraps Playwright Chromium for real mode; connects headless browser to the Frontend Server and bridges its WS client to the CLI's WS bridge.

</code_context>
