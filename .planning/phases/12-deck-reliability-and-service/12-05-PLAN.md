# Plan 12-05: Native service installer

<objective>
Convert backend execution into a native per-OS user service (systemd-user on Linux, launchd agent on macOS, Win32 service on Windows) controlled by a new `service` CLI command group. Reuse and extend `daemon.ts` for PID/token/child/config-path persistence. Foreground mode keeps terminal pretty logs; service mode emits structured ndjson to the native log.
</objective>

<title>Wire service command group (start/stop/restart/reload/update-config/status)</title>
<files>

- packages/cli/src/cli/commands/service/status.ts (new)
- packages/cli/src/cli/commands/service/run.ts (new)
</files>
<action>
1. `service start --config <path>`: resolves the absolute path (`path.resolve(process.cwd(), path)`), writes it into daemon state, then calls `platform.installUnit` (idempotent — if unit exists, just start it). The `--config` flag is required the first time; subsequent `start` calls without `--config` reuse the persisted path.
2. `service stop`: calls `daemon.terminateChildren({ timeoutMs: 5000 })`, then `platform.uninstallUnit`, then `daemon.writeState({ pid: 0, token: '', configPath: '', children: [] })`.
3. `service restart`: stop, then start (with `--config` if given, else persisted).
4. `service reload`: sends SIGHUP to the tracked PID (POSIX) or runs `platform.reloadUnit`; `run.ts` must listen for SIGHUP and re-read the persisted config. Add a `// ponytail: SIGHUP triggers config reload — run.ts must listen` comment in `run.ts`.
5. `service update-config --config <path>`: rewrites the unit's config arg, calls `platform.installUnit` again, then `restart`.
6. `service status`: prints `{ unitLoaded, pid, alive, configPath, childrenCount }` via the compact logger.
7. `service run`: the long-running entrypoint called by the unit. It is essentially the existing `run.ts` logic, but it does NOT spawn a new backend — it IS the backend; reads the persisted configPath, calls `daemon.writeState({ pid: process.pid, token, configPath, children: [] })`, and registers process exit handlers that write empty state. Frontend and emulator children are appended via `daemon.appendChild` as they spawn.
8. Each command file is thin (10-30 lines); heavy lifting lives in `daemon.ts` and the per-OS shell-outs.
</action>

`pnpm --filter @sireno-deck/cli exec tsc --noEmit` passes; `pnpm --filter @sireno-deck/cli exec sireno-deck service --help` lists all 7 subcommands.
</verify>
