# Plan 35-01: Keep The Physical Hardware Deck Live Between HTML Changes

<objective>
Deliver the main user-visible behavior for Phase 35: once a browser-backed deck reaches the physical Stream Deck, it should keep updating on hardware even when the DOM HTML itself has not changed. This slice must keep the mounted page alive, capture immediately when new HTML arrives, keep a steady-state recapture cadence around `250ms` between content changes, and feed those later frames through the existing per-key deduped hardware writer.
</objective>

## Tasks

<task id="35-01-01">
<title>Add a renderer-owned steady-state live capture mode that reuses the mounted page</title>
<files>
- packages/cli/src/render/browser-renderer.ts
- packages/cli/src/render/browser-renderer.test.ts
</files>
<action>
Extend `packages/cli/src/render/browser-renderer.ts` so browser-rendered hardware mode can keep recapturing from the same mounted page after the latest HTML version has already been rendered. Preserve the existing immediate capture when `updateDeck(...)` advances `latestVersion`, but add a renderer-owned steady-state cadence around `250ms` that can keep taking screenshots without re-running `renderPageHtml(...)` when the HTML/version has not changed. Add one explicit frame-delivery seam on the renderer for these live captures so callers do not need to poll from `start.ts`. Update `packages/cli/src/render/browser-renderer.test.ts` to prove unchanged steady-state recaptures do not call `setContent(...)` or `goto(...)` again, fresh HTML changes still capture immediately, and emulator/default mode does not start the new steady-state loop accidentally.
</action>

</verify>
<done>

</done>
</task>
