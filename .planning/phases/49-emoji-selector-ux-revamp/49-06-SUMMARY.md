# Plan 49-06 Summary

**Completed:** 2026-06-07

## What was built

A3 from the 49-CONTEXT post-ship amendments. The public `AddonButtonMethods.navigateToDeck` gains an additive optional `options?: { addToHistory?: boolean }` argument, and the internal `DeckController.navigateTo` gains a parallel `options?: { push?: boolean }` argument. When `addToHistory: false` (forwarded as `push: false`), the target deck replaces the top of the navigation stack in place, so the back stack does not accumulate entries for forward navigation that should be invisible to `goBack` (e.g. paginated emoji subdecks in 49-07). Default behavior is preserved for every existing caller.

## Decisions made

- `addToHistory: false` (public API) and `push: false` (internal API) are two different flag names for the same semantic. The public name speaks in terms of user-visible history; the internal name speaks in terms of stack mutation. Both default to `true` / `true`. This keeps the public addon API user-friendly without leaking the implementation detail (a `push` metaphor in the stack).
- The runtime factory wraps the controller call in try/catch and routes a `DeckNavigationError` to `showRuntimeButtonError`. This matches the existing pattern for `tap` / `dbl-tap` / `hold` (per the `RUNTIME_BUTTON_ERROR_CODES` record). The plan's task 49-06-03 explicitly asked for this; it's not gold-plating — it's the established seam for surfacing button-level runtime errors.
- The new `'navigateToDeck'` error code is 4109 (next sequential after 4108 `hold`). The error code numbering is internal; addons and users don't see it directly.
- Test 3 (`push: false` then `goBack`) was written from the plan's spec: "After `navigateTo('child', { push: false })` followed by `goBack()`, the active deck is `'main'`". The literal reading (active='main' after goBack) is correct, but the stack state is `['main']`, not `['main', 'child']` — replacement collapses the entry. This was a planning-phase brain-fart that the test caught; the implementation was right all along.
