# Plan 75.1-06 SUMMARY — Deck picker (UI + WS plumbing only)

## Status: Complete. Scope explicitly limited to UI + WS plumbing. Real surfaces-from-config is a runtime.ts rewrite follow-up (deferred).

### What this plan delivered

**Goal:** let the user pick which deck the emulator renders from the loaded config, so the new Vite-served emulator shell stops being a placeholder-date-time demo and becomes a real config explorer.

**1. WS protocol additions** (commit `27cd77b`)
- `DecksListMessageSchema` (CLI → renderer): `{type: 'decks-list', decks: Array<{id: string, name: string}>}` — broadcast on emulator startup and re-broadcast on every renderer reconnect.
- `SelectDeckMessageSchema` (renderer → CLI): `{type: 'select-deck', deckId: string}` — user clicked a deck in the picker.
- Both schemas added to the `MessageSchema` discriminated union in `packages/cli/src/render/protocol.ts`.
- `parseIncoming` in `packages/cli/frontend/src/ws-client.ts` extended to dispatch both new types.
- 4 new protocol tests (round-trips + empty-array rejection + empty-id rejection).

**2. CLI wiring** (commit `27cd77b`)
- `ViteDeckRenderer` extended with:
  - `sendDecksList()` — broadcasts the cached list to all open renderers + caches it for the next reconnect.
  - `onSelectDeck(handler)` — subscribes to incoming `select-deck` messages.
- `startEmulator` in `packages/cli/src/cli/commands/start.ts` now:
  1. Loads the runtime config (so it knows the deck IDs + names).
  2. Calls `sendDecksList({ decks: [...from config...] })` after spawning the bridge.
  3. Wires `onSelectDeck` to log + push a `deck-config` for the selected deck ID (currently placeholder surfaces — see "Scope limit" below).

**3. Emulator shell UI** (commit `27cd77b`)
- New `packages/cli/frontend-emulator/src/emulator/DeckSelector.tsx` (~70 lines).
- Mirrors the existing `DeviceSelector` button-row pattern (EmulatorShell header).
- Empty state: "awaiting decks-list from CLI" with a connection-status dot.
- On click: sends `{type: 'select-deck', deckId}` over the emulator's own WS client.
- `EmulatorShell.tsx` subscribes to `decks-list` and renders `<DeckSelector />` in the header.

**4. Iframe vertical-scroll fix** (rolled into commit `f66d2e8` of Plan 75.1-05 because the file move touched `IframeCanvas.tsx`)
- `iframeStyle.overflow: 'hidden'` + `frameStyle.overflow: 'hidden'` + `scrolling="no"` attribute on `<iframe>`.
- Kills the unwanted vertical scrollbar that appeared inside the emulator's deck iframe.

### Scope limit (intentional, deferred)

Picking a deck re-sends a placeholder `surfaces` array (current behavior — same as the picker-less version). The real implementation — translating `loadedConfig.config.decks[deckId].buttons[*]` into real `SurfaceSpec` per keyIndex — requires the **runtime.ts rewrite** that is currently blocked behind the `dom-host/` retirement phase. The deck picker is a clean UI + WS plumbing milestone; the runtime rewrite is the next phase.

User clarification on `startDaemon`: don't apply the deck picker to real-hardware `start` (the daemon already has overlay deck logic for active-app detection — chrome deck etc.). User's mental model: `start` uses real hardware and has its own deck selector pattern; `emulate` uses Vite and gets the new picker.

### How the deck picker flows end-to-end

1. User runs `pnpm cli:dev emulate --port 8912`.
2. CLI spawns WS bridge + Deck Vite (auto port) + Emulator Vite (8912).
3. CLI loads config → `sendDecksList({ decks: [{id: 'plain', name: 'Plain Deck'}, ...] })` broadcasts to all open renderers.
4. EmulatorShell receives `decks-list` → renders the DeckSelector header row.
5. User clicks a deck → DeckSelector sends `{type: 'select-deck', deckId: 'plain'}`.
6. CLI receives `select-deck` → logs it + (currently placeholder) sends back a deck-config for that deck ID.
7. The deck iframe inside IframeCanvas navigates to `/decks/<deckId>?ws=...&mode=emulate&device=...` and renders the deck.
