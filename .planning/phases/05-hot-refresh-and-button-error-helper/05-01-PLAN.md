# Plan 05-01: Truthful In-Process Runtime Reload

<objective>
Tighten the existing `start.ts` reload seam so the in-process daemon has one explicit runtime rebuild path for config-owned changes, without widening the claim to cover external raw-source edits. This slice matters because operators should be able to change config-owned inputs and see a truthful rebuild, while invalid reloads still fall back to the proven temporary full-deck error deck instead of corrupting runtime state.
</objective>

## Tasks

<task id="05-01-01">
<title>Make the daemon reload path an explicit single runtime rebuild seam</title>
<files>
- packages/cli/src/cli/commands/start.ts
</files>
<action>
Refactor `startDaemon()` so successful in-process reloads go through one named helper that owns: loading the next config/runtime inputs, snapshotting the current navigation state, stopping and replacing the previous runtime/session monitor/browser bindings, restoring navigation on the next runtime, and reinstalling watchers from the freshly loaded config graph. Keep the current behavior truthful: invalid config reloads must still format the validation error and call `runtime.showTemporaryErrorDeck(createTemporaryConfigErrorLines(error))`, while non-validation failures remain logged without pretending the reload succeeded.
</action>
