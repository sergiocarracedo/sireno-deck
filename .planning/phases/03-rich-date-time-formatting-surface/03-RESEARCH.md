## Common Pitfalls

### Letting Day.js chew through markup-looking text before shared `Text` sees it
**What goes wrong:** Tags like `<accent>` or `<danger>` can be mangled or treated as ordinary literal content in the wrong phase order, leaving the later shared parser with broken source text. [VERIFIED: `packages/cli/src/builtin-addons/date-time/format.ts`]  
**Why:** The live date-time seam today is a single `dayjs(date).format(config.format)` call, and Day.js expects literals to be explicitly escaped with square brackets when they should survive token processing untouched. [VERIFIED: `packages/cli/src/builtin-addons/date-time/format.ts`] [CITED: https://day.js.org/docs/en/display/format]  
**How to avoid:** Plan a preservation strategy before implementation: either segment the format string around markup or escape/preserve non-Day.js markup literals deliberately so shared `Text` receives intact markup after token expansion. [VERIFIED: `.planning/phases/03-rich-date-time-formatting-surface/03-CONTEXT.md`] [VERIFIED: Context7 `/iamkun/dayjs` docs query about escaping literals and preserving markup-like tokens]

### Turning shared `Text` parsing into implicit broad magic without a bounded grammar
**What goes wrong:** Always parsing strings can silently change every literal text surface in the repo, especially if the grammar is loose or best-effort. [VERIFIED: `.planning/phases/03-rich-date-time-formatting-surface/03-DISCUSSION-LOG.md`]  
**Why:** The current user choice is to always parse string children, not require an opt-in prop. That makes whitelist shape, invalid-markup behavior, and literal fallback correctness critical because every ordinary string path can encounter the parser. [VERIFIED: `.planning/phases/03-rich-date-time-formatting-surface/03-CONTEXT.md`] [VERIFIED: `packages/cli/src/ui/Text.tsx`]  
**How to avoid:** Keep the grammar tiny, explicit, and closed: tone tags only from the existing shared vocabulary, size tags only from existing `Text` sizes, one shorthand rule for `*...*`, one structural `|` line-break rule, one blink tag, and literal fallback for any invalid or unsupported input. [VERIFIED: `.planning/phases/03-rich-date-time-formatting-surface/03-CONTEXT.md`]

### Letting theme wrappers or per-widget code own inner markup rendering
**What goes wrong:** The shared contract fractures into widget-specific or theme-specific rich text behaviors, which breaks the repo’s canonical-`Text` direction. [VERIFIED: `.planning/phases/28-component-first-tsx-theme-ui-kit-cli/28-CONTEXT.md`]  
**Why:** `ThemeText` and theme presentation props already operate on outer text metadata only; date-time today simply supplies one flat string to `Text`. If Phase 3 adds a parallel parser in date-time or theme wrappers, the contract becomes duplicated immediately. [VERIFIED: `packages/cli/src/themes/default/ButtonFrame.tsx`] [VERIFIED: `packages/cli/src/builtin-addons/date-time/buttons/date-time.tsx`]  
**How to avoid:** Keep parsing and nested rendering in shared `Text`, and keep date-time narrow: Day.js expansion in, shared rich `Text` consumption out. [VERIFIED: `.planning/phases/03-rich-date-time-formatting-surface/03-CONTEXT.md`]

### Accepting best-effort recovery instead of one deterministic failure model
**What goes wrong:** Unknown tags, malformed nesting, and unsupported combinations can partially render, producing inconsistent output and brittle tests. [VERIFIED: `.planning/phases/03-rich-date-time-formatting-surface/03-DISCUSSION-LOG.md`]  
**Why:** The discussion briefly explored mixed failure models (`ignore them`, `hide formatting markers`), but the final locked decision is literal fallback for any invalid markup. Mixing rules would reintroduce ambiguity immediately. [VERIFIED: `.planning/phases/03-rich-date-time-formatting-surface/03-DISCUSSION-LOG.md`]  
**How to avoid:** Make invalidity binary. If the markup stream violates the whitelist, nesting, or supported-combination rules, render the original source string literally. [VERIFIED: `.planning/phases/03-rich-date-time-formatting-surface/03-CONTEXT.md`]

### Treating always-on blink as if it were accessibility-safe
**What goes wrong:** The product can intentionally ship motion that conflicts with modern reduced-motion guidance while the planning docs pretend otherwise. [CITED: https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion]  
**Why:** Current user intent is explicitly `Always blink`, but both MDN and modern-web guidance point toward honoring reduced-motion preference for non-essential animation. [VERIFIED: `.planning/phases/03-rich-date-time-formatting-surface/03-CONTEXT.md`] [VERIFIED: modern-web-guidance search results for `css blink animation prefers-reduced-motion accessibility text effects 2026`]  
**How to avoid:** Record this as an explicit product tradeoff in research and planning instead of burying it. Plans and verification should prove the chosen behavior honestly, even if it is not the recommended accessibility posture. [VERIFIED: this planning session]

## Existing Patterns in This Codebase

- **Shared `Text` is already the canonical text seam:** `packages/cli/src/ui/Text.tsx` already owns outer text semantics (`fit`, `size`, `tone`, `typography`, `align`) and threads them through theme presentation. Phase 3 should deepen that seam rather than add a second rich-text component by stealth. [VERIFIED: `packages/cli/src/ui/Text.tsx`] [VERIFIED: `.planning/phases/28-component-first-tsx-theme-ui-kit-cli/28-CONTEXT.md`]
- **Theme wrappers are metadata observers, not semantic owners:** `packages/cli/src/themes/default/ButtonFrame.tsx` and `packages/cli/src/config/theme.ts` already mirror outer text metadata without touching meaning. That is the correct boundary to preserve when nested markup arrives. [VERIFIED: `packages/cli/src/themes/default/ButtonFrame.tsx`] [VERIFIED: `packages/cli/src/config/theme.ts`]
- **Day.js is already the locked token engine for built-in date/time:** The live formatting seam is intentionally narrow and should stay that way. Phase 3 should not replace Day.js tokens with a second date language. [VERIFIED: `packages/cli/src/builtin-addons/date-time/format.ts`] [VERIFIED: `.planning/phases/29-built-in-addon-tsx-hard-cut-tailwind-cleanup/29-CONTEXT.md`]
- **The current date-time button is a simple pass-through into shared `Text`:** `packages/cli/src/builtin-addons/date-time/buttons/date-time.tsx` already formats once and renders one `Text`. That makes it a good integration seam for shared rich markup after token expansion. [VERIFIED: `packages/cli/src/builtin-addons/date-time/buttons/date-time.tsx`]
- **Tests already lock the single-field `format` contract:** `packages/cli/src/builtin-addons/date-time/index.test.ts` has already been reconciled to the live `format` field and current mounted rendering, so Phase 3 can build from that truth instead of resurrecting split-field drift. [VERIFIED: `packages/cli/src/builtin-addons/date-time/index.test.ts`]

## Recommended Approach

Split Phase 3 into two honest slices. First, add the shared `Text` whitelist parser/render seam itself: one small AST, one strict grammar, one deterministic literal-fallback rule, and one core renderer that maps tone tags onto the existing tone tokens and size tags onto the existing `Text` size vocabulary. [VERIFIED: `.planning/phases/03-rich-date-time-formatting-surface/03-CONTEXT.md`] [VERIFIED: `packages/cli/src/ui/Text.tsx`] Keep themes out of the inner semantics entirely. [VERIFIED: `packages/cli/src/themes/default/ButtonFrame.tsx`]

Second, integrate date-time truthfully on top of that shared seam. Keep one `format` field, preserve Day.js as the token engine, and add an implementation path that protects markup literals around token expansion before feeding the resulting string into shared `Text`. [VERIFIED: `packages/cli/src/builtin-addons/date-time/format.ts`] [CITED: https://day.js.org/docs/en/display/format] Prove the phase with shared `Text` parser tests plus date-time passthrough coverage and one end-to-end review path that exercises nesting, literal fallback, and blink behavior honestly. [VERIFIED: `packages/cli/src/builtin-addons/date-time/index.test.ts`]

One thing should stay explicit in planning: always-on blink is the chosen product behavior right now, but it is not aligned with current reduced-motion guidance. That should remain visible in the plans and verification notes rather than getting silently normalized into “accessibility-safe” wording. [VERIFIED: `.planning/phases/03-rich-date-time-formatting-surface/03-CONTEXT.md`] [CITED: https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion]
