# Plan 12-06: Emulator visibility

<objective>
Surface the addon's metadata (source path, decks with overlay/paginated flags, button counts) and the resolved config path in the emulator. Use a wrapped flow of colored tags with a legend, reusing the existing tag primitives.
</objective>

## Tasks

<task id="12-06-01">
<title>Bridge: addonInventory + configPath messages</title>
<files>
- packages/cli/src/cli/addon-handler-bridge.ts
- packages/cli/src/cli/methods.ts
- packages/cli/src/cli/commands/run.ts
</files>
<action>
1. In `addon-handler-bridge.ts`, add `publishAddonInventory()` that walks the loaded addons via `AddonRegistry.list()` (or equivalent) and emits a bridge message `{ type: 'addonInventory', addons: [{ name, source, decks: [{ id, isOverlay, paginated, buttons: number }] }] }`. Call it after manifest load and on addon reload.
2. In `methods.ts`, add a `getConfigPath` RPC that returns the cwd-resolved absolute path. Use `path.resolve(process.cwd(), opts.config ?? persistedConfigPath)`. Call it from the emulator's `bridge.ts` on connect.
3. In `run.ts`, where `ConfigWatcher` fires on file change, re-call `publishAddonInventory()` (decks may have changed shape) and the emulator's bridge re-fetches `getConfigPath`.
4. Add `// ponytail: addonInventory is the canonical metadata channel — SidePanel/AddonsPage do not parse manifests themselves` comment.
</action>
<verify>
`pnpm --filter @sireno-deck/cli exec tsc --noEmit` passes; `rg "addonInventory|getConfigPath" packages/cli/src/cli/` lists the publish and RPC sites.
</verify>
<done>
Bridge carries the addon metadata + config path; runtime publishes on load/reload.
</done>
</task>

<task id="12-06-02">
<title>AddonsPage wrapped colored tag flow + legend</title>
<files>
- packages/cli/emulator/src/SidePanel.tsx
- packages/cli/emulator/src/pages/AddonsPage.tsx
- packages/cli/emulator/src/__tests__/AddonsPage.test.tsx (new)
</files>
<action>
1. In `AddonsPage.tsx`, replace any list/table layout with a single `flex-wrap: wrap` container of `<Tag>` primitives. For each addon:
   - A bold addon tag (`bg: var(--accent)`) showing the addon name.
   - A subdued source tag (`bg: var(--surface-2)`) showing the absolute source path immediately after.
   - For each deck: a deck tag with `bg` differing by `isOverlay` (overlay = warning color, regular = neutral). Append a small `paginated` marker if true.
   - For each deck, one button tag per slot count (e.g. `12 buttons`).
2. In `SidePanel.tsx`, render a 4-row legend above the Addons page when the user is on that page: addon source/name, regular deck, overlay deck, button. Each legend entry is a small colored swatch + label.
3. Reuse the existing `<Tag>` primitive from the emulator's component library; if it lacks color props, add them (don't create a parallel tag system).
4. Add `// ponytail: single wrapped flow keeps long addon names readable without horizontal scroll` comment.
5. Write `AddonsPage.test.tsx` with two addons (one with an overlay deck, one without) and assert the rendered output contains the addon name, source path, deck colors, and the button count.
</action>
<verify>
`pnpm --filter @sireno-deck/cli exec vitest run packages/cli/emulator/src/__tests__/AddonsPage.test.tsx` passes.
</verify>
<done>
AddonsPage renders the wrapped tag flow with legend; tests cover overlay vs regular distinction.
</done>
</task>
