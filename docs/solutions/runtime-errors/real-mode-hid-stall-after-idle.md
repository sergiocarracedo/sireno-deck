date: 2026-08-24

category: docs/solutions/runtime-errors/
module: cli/src/outputClient/real
problem_type: missing_signal
component: device_input
severity: high
symptoms:

- "After running for hours, hardware buttons stop responding. Frontend still renders the active deck and WS bridge is alive (heartbeat rebroadcasts continue)."
- "`tail -F $XDG_RUNTIME_DIR/sireno-deck/service.log` shows no `real mode: key event received` lines for newly-pressed buttons."
- "`[runtime] invokeAction resolved` log lines stop appearing for hardware presses; emulator clicks (and frontend UI clicks via `invokeAction`) still log normally."
- "Reproduces more reliably on Linux laptops after the OS suspends / resumes USB peripherals or after long idle on battery."
- "After the stall-recovery logic fires (`real mode: device reconnected after stall` logged), the daemon may exit with `FATAL unhandledRejection` and a log line that shows no `reason`/`err` context. See `crash-during-recovery` below."
- "Frontend visually freezes on the device after the recovery while emulator clicks and emulator-side gesture detection keep working. Hardware buttons still trigger actions — the gesture listener is on the _new_ handle — but the Stream Deck display never updates because the renderer is still writing to the _closed_ handle. See `frontend-frozen-after-recovery` below."
  diagnosis:
- "Default log level is `info`; the `real mode: key event received` trace was previously emitted at `debug` and silently filtered. The first visible signal after the bump is `real mode: key event received` stopping — which means the device-onKeyEvent callback never fires."
- "Check at the kernel level: `lsusb -t` for `suspend` near the Stream Deck, or `cat /sys/bus/usb/devices/<bus>-<port>/power/control`. If `auto` or `suspend`, the kernel put the device to sleep."
- "Cross-check with `sudo evtest /dev/input/by-id/usb-Elgato_Stream_Deck_*-event-if00`. If evtest sees the press but the daemon doesn't, the issue is upstream of node-hid; if evtest doesn't see it, the kernel/USB stack is the issue."
- "If the FATAL line shows no `err`/`reason` context, the human-friendly logger formatter was dropping it. The JSON output (service.log on disk) carries the `reason` field but the formatter used to only look at `err`. The current formatter falls back to `entry[\"reason\"]` and renders it as `err: <type>: <message>`; the `unhandledRejection` handler also mirrors the cause to stderr via `process.stderr.write(...)` (sync write) so the detail survives even if pino's async buffer is truncated by `process.exit`.
- "If the device visually freezes after the recovery (buttons still work, frontend still renders correctly in the browser): the Stream Deck is displaying the last buffer that _was_ successfully pushed before the close, because `BrowserRenderer` captured `device` at construction time and never refreshed it. After the swap the renderer keeps writing to the closed handle; the per-write `.catch` from the previous round swallows the rejections but doesn't redirect them to the new handle. After the fix (Option A below) the renderer takes a `getDevice: () => DeviceSink` accessor that is called on every tick — same pattern as `gestureUnsubscribe.current` for the gesture side — and the swap is automatic."
  root_cause: "USB autosuspend puts the Stream Deck's HID endpoint to sleep after long idle. node-hid reads stall without surfacing errors, so `device.onKeyEvent` stops firing. The daemon process is alive (the heartbeat and renderer keep working), but the device side of the chain is dead. A secondary crash pattern appeared during the recovery itself: fire-and-forget async calls into the now-closed device (`void this.device.setBrightness(value)`, `void opts.runtime.dispatchGesture(...)`) and per-tick writes (`void fillKeyBuffer(...)`) had no `.catch`, so a rejection that surfaced mid-recovery exited the daemon instead of being logged. A tertiary symptom is the **frozen display**: the renderer held a captured device reference and kept writing to the closed handle after the recovery."
  fix: "Six layers, applied together: (1) Bump `real mode: key event received` from `debug` to `info` so this class of regression is visible by default. (2) Add a HID stall detector (`packages/cli/src/device/hid-stall-watcher.ts`) — a self-healing timer that force-closes and reopens the device after 5 min of zero events (skipped while the session is locked). (3) Wrap the recovery callback body in an outer `try/catch` and add `.catch` to every fire-and-forget device call (`setBrightness`, `dispatchGesture`), to the renderer's per-write `fillKeyBuffer`, and to the watcher's own promise chain (sync + async rejection paths) so a stray throw during the recovery window is logged, not fatal. (4) Add `.catch` to the active-app providers' `void snapshot().then(...)` chains (linux/darwin/windows) so a subscribe-handler throw can never escape the poll loop. (5) Add a udev rule (`packages/cli/src/device/linux-udev.ts`) that disables USB autosuspend for the Elgato vendor (0fd9) — eliminates the most common cause at the kernel level. (6) Surface the unhandled-rejection reason on the FATAL line. (7) Switch `BrowserRenderer` to take `getDevice: () => DeviceSink` instead of a captured device; introduce a `deviceRef` in `RealOutputClient.init`; on recovery, update `deviceRef.current` and call `renderer.resetTracker()` so the next tick pushes every key (the tracker would otherwise compare against the buffer that was supposedly written to the _previous_ handle — which never made it — and skip the write, leaving the deck visually frozen)."
  prevention: "For any long-lived device-input handler in a daemon, default to `info` for the per-event trace (not `debug`). Add a stall detector that re-opens the device after a configurable idle window. For USB peripherals on Linux, ship a udev rule that disables autosuspend for the relevant vendor — autosuspend is the most common silent-killer of HID handlers. **Every `void Promise<...>` in a long-lived daemon is a code smell** — always attach a `.catch((err) => logger.warn(...))` so the failure is observable. Same rule for the `void` discards that wrap `setInterval` / `setTimeout` callbacks that fire async work: prefer an explicit `Promise.resolve().then(...).catch(...)` chain. **Never capture a device handle in a long-lived consumer**: pass a `() => Device` accessor instead, so a hot-swap is picked up automatically. The same shape works for any future 'switch X' scenario (two physical decks, virtual-to-real transition, ...)."
