# Plan 75.1-03: Router navigation + history vs overlay

## Goal

Add React Router v7 to the frontend and wire history vs replace semantics for regular vs overlay decks. Prove the distinction on real hardware with a back-button press.

## Context

Plans 01-02 proved the three-layer pipeline and the WS bridge. This plan adds the navigation layer: regular decks push history; overlay decks replace. The architecture diagram calls this out explicitly ("remember regular decks has history memory, but no overlay decks").

### Task 2: History vs replace on regular vs overlay decks

<files>
- packages/cli/src/render/protocol.ts (modify — add navMode to deck-config)
- packages/cli/frontend/src/router.tsx (modify — use replace for overlay decks)
- packages/cli/frontend/src/hooks/useDeckNavigation.ts (new)
- packages/cli/src/cli/commands/start.ts (modify — derive navMode from existing overlay semantics)
</files>

<action>
1. Add `navMode: 'push' | 'replace'` to `DeckConfigMessage` in `protocol.ts`. Default is `'push'`.
2. **Do NOT add a new `overlay` schema field.** The overlay concept is already encoded via `process_names` + `autoShow: false` (existing active-app overlay deck contract; see `packages/cli/src/deck/runtime.ts:1462-1471`). A new `overlay?: boolean` would overlap with this and create undefined behavior for decks without `process_names`.
3. In `start.ts`, derive `navMode` from existing semantics:
   ```ts
   const isOverlayDeck = (deck: CoreDeckConfig) =>
     Array.isArray(deck.process_names) && deck.process_names.length > 0 && deck.autoShow === false;
   // ...
   const navMode = isOverlayDeck(activeDeck) ? 'replace' : 'push';
   ```
4. In `useDeckNavigation` (new hook):
   - On every incoming `deck-config`, call `navigate('/decks/' + deckId, { replace: navMode === 'replace' })`.
   - `useNavigationType()` returns the navigation type (PUSH / POP / REPLACE). Components can check this if they need to react to back-vs-forward.
5. Verify that overlay decks (those with `process_names` + `autoShow: false`) do not appear in browser history: pressing the browser back button skips them.
</action>

<verify>
- Config has decks A, B (regular) and C (overlay). Tap A → tap button leading to B → B renders, history is `[A, B]`. Press back → A renders, history is `[A]`.
- Tap A → tap button leading to C (overlay) → C renders, history is `[A]` (replace, not `[A, C]`). Press back → A renders.
- Mixed sequence: A → B → C (overlay) → press back → B renders, history is `[A, B]`. Press back → A renders.
</verify>

<done>
Regular decks push history; overlay decks replace. Verified end-to-end via the WS bridge → React Router integration.
</done>

## Risks

- **React Router + Vite HMR conflict**: HMR sometimes doesn't cleanly re-mount the router. Mitigation: top-level `<App>` uses a key derived from the HMR boundary so a full re-mount happens on HMR.
- **`useNavigationType()` flips during HMR**: false signal to back-button components. Mitigation: ignore `useNavigationType()` for 500ms after HMR re-mount.
- **Client-side history stack drift from server-side truth**: if a `deck-config` is lost in transit, the client stack is ahead/behind the server's. Mitigation: server sends a `state` message with the full stack on every `deck-config`; client rebuilds its stack from that.

## Demo

Tap a button on deck A → deck B renders, browser back returns to A. Tap a button that summons overlay C → C renders, browser back returns to the previous regular deck (skips C). Press the hardware back button → same behavior, driven from the CLI.
